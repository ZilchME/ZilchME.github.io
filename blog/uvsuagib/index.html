工业设备时序数据存储分片分表设计

工业 IoT、MES、设备监控、AI 训练平台这类系统，在项目早期通常都会采用一种非常自然的设计：

所有聚合后的设备时序数据放在一张表里

例如：

aggregated_device_data (
    id,
    device_id,
    metric,
    value,
    timestamp,
)

这种设计在数据量不大时非常合理：

  • 模型简单
  • 查询直接
  • 开发成本低
  • MyBatis / JPA 很容易接入

但随着设备数量增加、采样周期缩短、训练数据长期保留，单表方案最终一定会遇到瓶颈。

单表方案的局限与演进动机

当前系统承载的三类查询

当前聚合表主要承载三类查询：

单设备趋势查询

WHERE device_id = ?
AND timestamp >= ?
AND timestamp < ?

例如：查看某台设备最近 7 天温度曲线

多设备联合分析

WHERE device_id IN (...)
AND timestamp >= ?
AND timestamp < ?

例如：查看整条产线多个设备的压力波动

AI 训练数据导出

WHERE timestamp >= ?
AND timestamp < ?
AND device_id IN (...)
ORDER BY timestamp, device_id, metric

例如：导出过去半年设备数据生成 Parquet

单表为什么一定会出问题

如果聚合数据永不过期，随着业务增长，会同时出现三个问题。

数据量持续膨胀

索引越来越重

即使建立索引：

(device_id, timestamp)

随着索引树持续增长：

  • 查询 IO 增加
  • Buffer Pool 命中下降
  • 排序成本增加
  • 范围扫描越来越慢

工艺维度查询越来越差

工业系统有一个很典型的特点：查询通常不是"随机设备"，而是"同工艺链路设备"

但单表只有 device_id，系统只能先查所有设备再拼一个巨大的 device_id IN (...)

随着设备数增加：IN 查询越来越重，SQL 越来越长，优化器越来越难选执行计划

为什么不能直接按 device_id 分片

很多系统第一反应是 device_id hash 分片，这对"随机设备查询"有效。

但工业系统的问题在于：同一个工艺组下的设备会被打散，需要访问大量分片，服务层聚合结果

这会让查询复杂度暴增、网络开销增加、排序与分页困难、导出性能下降

核心架构设计

工艺组分片

真正合理的设计是：设备属于工艺组、工艺组决定数据分片

先建立：

device_id -> process_group_id

例如：

  • device_001 -> coating_line_01
  • device_002 -> coating_line_01
  • device_003 -> coating_line_01
  • device_101 -> welding_line_02

然后：

process_group_id -> shard

例如：

hash(process_group_id) % 128

最终：

coating_line_01
  → logical_shard_07
  → agg_db_01.table_03

这样做到了同工艺组设备尽量落在同一物理分片

时间分区

工艺组分片解决的是横向扩展和工艺局部性，但它不能解决单个分片数据长期增长，所以还需要时间分区

例如每个分片内部：

PARTITION BY RANGE COLUMNS(timestamp)

按月分区：

PARTITION p202601 VALUES LESS THAN ('2026-02-01')
PARTITION p202602 VALUES LESS THAN ('2026-03-01')

这样 2026-02 查询只扫描 p202602，MySQL 会自动做 Partition Pruning（分区裁剪）

降低范围扫描

原来扫描整张百亿表，现在只扫描某个月分区

控制索引规模

每个分区维护自己的局部索引，索引树更小查询更稳定

历史归档方便

例如：

ALTER TABLE xxx DROP PARTITION p202401;

比：

DELETE FROM xxx WHERE timestamp < ...

快很多。

为什么引入逻辑分片

不要直接：

hash(process_group_id) % 4

因为以后扩容会导致大量数据重新分布

更合理：

process_group_id
  → logical_shard 0..127
  → physical_db/table

例如：

  • logical_shard 0-15 -> agg_db_00
  • logical_shard 16-31 -> agg_db_04

扩容时只迁移部分 logical shard 业务层完全无感知。

最终架构

device_id
  ↓
device_shard_route
  ↓
process_group_id
  ↓
logical_shard
  ↓
physical_db + physical_table
  ↓
aggregated_device_data_xxx
  ↓
按 timestamp 时间分区

数据表与路由设计

路由表

核心路由表：

device_shard_route (
    device_id,
    process_group_id,
    factory_id,
    line_id,

    logical_shard,
    physical_db,
    physical_table,

    effective_from,
    effective_to
)

作用：

设备 -> 工艺组 -> 分片

聚合表演进

原表：

aggregated_device_data (
    device_id,
    metric,
    value,
    timestamp
)

演进后：

aggregated_device_data_xxx (
    process_group_id,
    device_id,
    metric,
    timestamp,
    value
)

这里最重要的是冗余保存 process_group_id，这样：

WHERE process_group_id = ?
AND timestamp >= ?

就能直接命中目标分片。

唯一键调整

原唯一键：

UNIQUE(device_id, metric, timestamp)

演进后：

UNIQUE(
    process_group_id,
    device_id,
    metric,
    timestamp
)

作用：保证幂等写入 Kafka / MQ 重投不会产生重复聚合数据。

业务链路改造

写入链路

原来：

aggregatedMapper.batchInsert(dataList);

现在：

  1. device_id 查路由表
  2. 获取 process_group_id
  3. 按 physical_db/table 分组
  4. 分片批量写入

即：

DataAggConsumer
  → AggregatedDataRepository
    → 路由
    → 分片分发

查询链路

原来：

WHERE device_id IN (...)

现在：

  1. deviceIds -> route
  2. 按 shard 分组
  3. 各分片本地查询
  4. 服务层 merge

如果按工艺组查询则能直接命中单分片，这是整个架构最大的收益之一。

训练数据导出

deviceIds
  → shard group
  → shard local cursor scan
  → parquet shard
  → manifest.json

训练服务不关心底层多少分片，只消费 manifest

总结

工业设备时序数据和普通业务数据最大的区别在于：

  • 数据持续增长
  • 几乎永不删除
  • 查询强依赖时间范围
  • 且具有明显工艺局部性

因此，"工艺组分片 + 时间分区"本质上是在解决三个问题：

工艺局部性

让同工艺设备尽量落在同一分片，减少跨库查询。

长期数据规模控制

通过时间分区限制单分区索引规模，保证长期查询性能稳定。

水平扩展能力

通过 logical shard 实现在线扩容、冷热分离、历史迁移

真正适合工业场景的架构通常都会演进到工艺组分片 + 时间分区

其中：

  • 工艺组分片解决横向扩展和工艺局部性
  • 时间分区解决长期数据增长和范围扫描
  • 逻辑分片解决未来扩容
  • 路由层解决业务无感知迁移

这也是很多大型工业 IoT、MES、数据中台最终都会走向的时序存储演进方向。
