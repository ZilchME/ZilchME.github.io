## 为什么 MySQL InnoDB 索引使用 B+ 树，而不是跳表？

\*\*关键在于数据库按页读写数据：B+ 树将大量索引项集中在一个页中，通过较大的扇出降低树高，更适合磁盘和页缓存。\*\*跳表也能高效查找、遍历范围，但常见的逐节点指针实现更适合内存访问，不能仅凭两者都有对数级查找就认为它们等价。

### 1. 页组织与树高

InnoDB 默认页大小为 16 KiB。B+ 树的非叶子页保存分隔键与子页引用，一页可指向很多子页；叶子页保存数据记录或二级索引记录。每下降一层，通常可以把搜索范围缩小很多，因而大表的索引树仍可以很矮。

聚簇索引叶子页保存行记录；二级索引叶子页保存二级索引键和主键等信息。二级索引不覆盖查询字段时，还需要利用主键回到聚簇索引查找，这就是回表。根页和部分内部页通常可以缓存在 Buffer Pool 中，所以**树高不等于每次查询实际发生的磁盘 I/O 次数**。[参考：InnoDB 索引物理结构](https://dev.mysql.com/doc/refman/8.4/en/innodb-physical-structure.html)

### 2. 与跳表的对比

| 维度 | B+ 树 | 常见跳表实现 |
| --- | --- | --- |
| 数据组织 | 一个页容纳多条记录或多路分支 | 节点通过多层指针连接 |
| 外存访问 | 较高扇出减少需要访问的页层数 | 节点分散时，指针追踪可能触及更多页 |
| 范围查询 | 定位首个叶子页，再沿叶子页链遍历 | 定位起点后沿底层链遍历，同样适合范围查询 |
| 插入与维护 | 可能需要页分裂、合并与索引维护 | 维护各层指针，排名跳表还需维护跨度 |
| 典型使用环境 | 数据库页式存储与缓存 | Redis ZSet 等内存有序结构 |

因此不能说“跳表不能范围查询”，也不能说 B+ 树的每次读写都更快。选择取决于存储介质、节点布局、缓存与并发控制。跳表也可以设计成适合外存的变体；这里比较的是常见实现及 InnoDB 的页式存储需求。

\*\*面试回答：\*\*InnoDB 使用 B+ 树，主要是为了适配页式 I/O。非叶子页可容纳大量分隔键，扇出大、树高低；叶子页有序连接，适合范围扫描。跳表在内存中很有效，但常见指针结构的页局部性与外存访问成本不如这种页式布局。两者都能做有序查询，不能单看平均时间复杂度决定数据库索引结构。

## 如何估算 10 亿条数据的 B+ 树有多少层？

\*\*不能只根据行数给出固定答案，必须先说明索引类型、页大小、键宽、行大小和页利用率。\*\*估算方法是先算叶子页数量，再用内部页扇出逐层向上推导。下面把根页和叶子页都计为一层。

### 1. 通用估算方法

设：

* `N`：记录数量。
* `L`：每个叶子页平均容纳的记录数。
* `F`：内部页的平均有效扇出，即平均子页数量。
* `H`：从根到叶的层数。

忽略根页等边界差异，容量可近似表示为：

$$
N \approx L \times F^{H-1}
$$

$$
H \approx 1 + \left\lceil \log_F \left(\left\lceil \frac{N}{L} \right\rceil\right) \right\rceil
$$

实际应按逐层向上取整的页数计算；该公式用于量级估算，并不是对所有页面布局的精确描述。

### 2. 聚簇索引的示例

假设页大小为 16 KiB，每条叶子记录约 1 KiB，内部索引键和子页引用较小，暂取平均有效扇出 `F = 1000`，叶子记录数简化取 `L = 16`。这里为方便计算暂未精确扣除页头、记录头、目录和预留空间：

| 层数 | 近似可容纳记录数 |
| --- | --- |
| 2 层：根 → 叶 | `1000 × 16 = 1.6 万` |
| 3 层：根 → 内部页 → 叶 | `1000² × 16 = 1600 万` |
| 4 层：根 → 两层内部页 → 叶 | `1000³ × 16 = 160 亿` |

在这些假设下，10 亿条数据超过三层容量、没有超过四层容量，因而估算为 **4 层**。扣除开销后单页记录数会变少，但不能因此脱离具体参数断言一定变成 5 层。

### 3. 为什么有人算出三层？

二级索引叶子记录可能只包含较短索引键与主键，一页能容纳的条目远多于整行记录；如果使用接近每页 1000 条、内部扇出也接近 1000 的理想假设，三层容量就接近 10 亿。但它处于边界，页开销、页利用率、键长度稍有变化，结果就可能改变。

因此“三到四层”只是某些参数下的常见量级，面试中应明确计算前提。宽主键会增大二级索引记录，宽联合索引也会降低扇出；实际高度应结合索引页与存储统计确认。多层索引的上层页若命中缓存，实际物理读仍可能很少。

## 如何避免死锁

死锁通常需要同时满足四个条件：

* \*\*互斥：\*\*资源同一时间只能被一个线程持有。
* \*\*请求并保持：\*\*线程持有一个资源时，又去申请其他资源。
* \*\*不可剥夺：\*\*已持有的资源不能任意强制收回，只能在合适时机释放。
* \*\*循环等待：\*\*多个线程形成环形等待，比如 A 等 B 的锁，B 又等 A 的锁。

所以避免死锁，本质上就是破坏这四个条件中的至少一个。实际开发中最常用的是破坏“循环等待”和“请求并保持”。

第一种方式是 **固定加锁顺序**。

比如两个线程都需要锁 A 和锁 B，就规定所有线程必须先拿锁 A，再拿锁 B，不能有的线程先拿 A，有的线程先拿 B。

```java
synchronized (lockA) {
    synchronized (lockB) {
        // 业务逻辑
    }
}
```

只要所有地方都遵守同样的加锁顺序，就不会形成循环等待。

第二种方式是 **减少锁嵌套**。

能不在一个锁里面再申请另一个锁，就尽量不要嵌套。可以在不破坏业务原子性的前提下拆分操作，缩小锁范围；如果两个资源必须一起保持一致，不能为了减少嵌套直接拆成互不关联的临界区。

```java
synchronized (lockA) {
    // 只处理和 A 相关的共享数据
}

// 释放 lockA 后，再处理其他逻辑
```

第三种方式是 **一次性申请所有资源**。

如果业务允许，可以在执行前先判断资源是否都能获取，获取不到就不持有任何资源，避免“拿着一个锁等另一个锁”。

第四种方式是使用 **tryLock + 超时机制**。

`ReentrantLock` 支持 `tryLock()`，如果一定时间内拿不到锁，就释放已经持有的锁并重试，避免无限等待。

```java
if (lockA.tryLock(1, TimeUnit.SECONDS)) {
    try {
        if (lockB.tryLock(1, TimeUnit.SECONDS)) {
            try {
                // 业务逻辑
            } finally {
                lockB.unlock();
            }
        }
    } finally {
        lockA.unlock();
    }
}
```

超时后应释放已持有的其他锁，并决定失败返回还是有限重试；重试可加入随机退避，避免多个线程反复同步争抢形成活锁。示例中的 `InterruptedException` 需要向上抛出或妥善处理。`tryLock` 不会强行释放其他线程的锁，它只是提供有界等待与主动退出的机会。[参考：ReentrantLock](https://docs.oracle.com/en/java/javase/25/docs/api/java.base/java/util/concurrent/locks/ReentrantLock.html)

第五种方式是 **避免长事务或长时间持锁**。

持锁期间不要做耗时操作，比如远程 RPC、数据库慢查询、大文件 IO、网络请求等。因为这些操作时间不可控，会增加锁等待和死锁概率。

不推荐这样：

```java
synchronized (lock) {
    // 修改共享变量
    callRemoteService(); // 不建议在锁内做远程调用
}
```

应该尽量把耗时操作放到锁外。

第六种方式是 **使用更合适的并发工具**。

在语义满足需求时，可以使用并发容器、原子类等减少手写锁。它们不自动保证多资源操作的整体原子性；读写锁还要避免持有读锁后直接等待写锁等不安全的升级方式，不能认为换一种工具就一定没有死锁。

常见工具有：

`ConcurrentHashMap`、`AtomicInteger`、`LongAdder`、`BlockingQueue`、`ReadWriteLock`、`Semaphore`、`CountDownLatch` 等。

第七种方式是 **数据库场景中保持一致的更新顺序**。

数据库死锁也很常见。比如事务 A 先更新订单表再更新库存表，事务 B 先更新库存表再更新订单表，就容易死锁。

应该统一顺序，比如所有事务都先更新库存，再更新订单。批量更新多条记录时，也尽量按主键排序后再更新。

```sql
-- 尽量统一顺序，例如都按 id 从小到大更新
update account set balance = balance - 100 where id = 1;
update account set balance = balance + 100 where id = 2;
```

**避免死锁的核心是破坏死锁产生条件，实际开发中最常用的是固定加锁顺序、减少锁嵌套、缩小锁粒度、使用 tryLock 超时机制、避免锁内执行耗时操作。数据库事务中也要统一访问表和行的顺序，控制事务大小，必要时增加重试机制。**

### 已经发生死锁时如何排查？

Java 中可以用 `jstack <pid>` 或 `jcmd <pid> Thread.print -l` 获取线程转储，观察线程正在等待及持有的锁，寻找环形依赖。工具对不同锁和运行时状态的可见性不同，未直接报告死锁不代表没有业务层面的资源等待循环。

MySQL 可通过 `SHOW ENGINE INNODB STATUS` 查看最近一次死锁，结合事务 SQL、锁住的索引与记录分析；需要持续记录时，可以评估开启 `innodb_print_all_deadlocks`。InnoDB 检测到死锁后通常选择一个事务回滚，应用应在确认幂等与外部副作用处理方式后，有限重试**整个事务**，而不是只重发最后一条失败 SQL。超时与死锁也应分别处理，不能将所有锁等待都认定为死锁。[参考：InnoDB 死锁](https://dev.mysql.com/doc/refman/8.4/en/innodb-deadlocks.html)

## 事务有哪些隔离级别，分别解决什么问题？

### 1. 先区分三种读取异常

| 问题 | 含义 | 示例 |
| --- | --- | --- |
| 脏读 | 读到其他事务尚未提交的修改 | 读到一次后来回滚的余额变更 |
| 不可重复读 | 同一事务两次读同一行，看到其他事务提交的不同值 | 两次查询同一订单金额不同 |
| 幻读 | 同一事务重复执行范围查询，符合条件的行集合发生变化 | 两次查询待处理订单，多出其他事务插入的记录 |

### 2. 标准隔离级别

| 隔离级别 | 脏读 | 不可重复读 | 幻读 | 特点 |
| --- | --- | --- | --- | --- |
| 读未提交（RU） | 可能 | 可能 | 可能 | 允许读到未提交数据 |
| 读已提交（RC） | 避免 | 可能 | 可能 | 每次读取以当次可见的已提交数据为基础 |
| 可重复读（RR） | 避免 | 避免 | 标准定义仍可能 | 同一事务内重复读取已读数据保持一致 |
| 串行化 | 避免 | 避免 | 避免 | 达到可串行执行的隔离效果，并发限制通常更多 |

这里是标准层面的概括，具体数据库的实现可能更强。不能把标准 RR 对幻读的描述直接照搬成“InnoDB 默认隔离级别完全不处理幻读”。

### 3. InnoDB 的 RR 如何工作？

InnoDB 默认使用 RR，但业务也可以改成 RC，排查时应查询实际会话配置。

* \*\*普通一致性读：\*\*通常通过 MVCC 提供快照。RR 下第一次一致性读建立的快照在事务内复用；RC 下，每次一致性读通常创建新的快照。事务自身的修改对自己可见，并存在 DDL 等边界，不能理解成“事务里任何 SQL 永远看到同一份旧数据”。
* **锁定读和写操作：**`SELECT ... FOR UPDATE`、`SELECT ... FOR SHARE` 以及更新、删除，不是简单地读取旧快照。RR 下范围搜索通常使用记录锁和间隙锁组合的 next-key lock，约束其他事务向被保护间隙插入；唯一索引唯一等值命中等情况可能只锁记录。
* \*\*两种机制各有范围：\*\*快照使重复的一致性读不看到后来插入的行；范围锁防止其他事务在当前锁定范围内插入。混用快照读、锁定读和写操作时，不能推导出所有读取结果都完全一致。

例如，事务 A 在 RR 下两次普通查询订单列表，期间事务 B 插入并提交新订单，A 的第二次一致性读通常仍使用原快照，不会因为 B 的插入多出记录。若 A 要确保查询范围内的数据不被并发插入影响后续操作，应根据业务使用合适的锁定读和约束，而不是仅依靠旧快照。[参考：InnoDB 隔离级别](https://dev.mysql.com/doc/refman/8.4/en/innodb-transaction-isolation-levels.html)、[一致性非锁定读](https://dev.mysql.com/doc/refman/8.4/en/innodb-consistent-read.html)

### 4. 隔离级别不是业务并发控制的全部

避免重复下单要使用合理的唯一约束或幂等设计；扣库存通常需要条件更新、版本控制或合适的锁。即使使用 RR，也不能把“读取库存 → 应用内减一 → 直接覆盖”的多步流程视为天然安全。不同事务对多行数据的并发检查，还可能涉及写偏差等更复杂问题。

\*\*面试回答：\*\*四种隔离级别是读未提交、读已提交、可重复读和串行化。主要围绕脏读、不可重复读和幻读提供不同隔离保障。InnoDB 默认 RR，一致性读使用 MVCC 快照，锁定范围查询则可以通过 next-key lock 保护范围；具体业务仍需要唯一约束、原子更新和必要的加锁，不能只靠隔离级别兜底。

## ping 使用什么协议，属于哪一层？

`ping` 使用的是 **ICMP 协议**，全称是 **Internet Control Message Protocol，互联网控制报文协议**。

它位于 **网络层**，和 IP 协议同一层，通常被认为是 IP 协议的辅助协议。

`ping` 的基本过程是：

```text
主机 A 发送 ICMP Echo Request
主机 B 收到后返回 ICMP Echo Reply
主机 A 根据返回结果判断网络是否可达、延迟是多少、是否丢包
```

也就是：

```text
ping 请求包：ICMP Echo Request
ping 响应包：ICMP Echo Reply
```

### 能 ping 通代表业务服务正常吗？

不能。常规 IPv4 `ping` 使用 ICMP Echo Request / Reply，IPv6 使用 ICMPv6；这些报文由 IP 承载，属于网络层，不使用 TCP 或 UDP 端口。因此 ping 通只能说明当时存在 ICMP 往返能力，并不保证 HTTP、数据库等应用可用。ping 不通也不一定代表主机离线，可能是防火墙过滤、限速或对端禁止响应；应结合业务端口与应用请求排查。[参考：ICMP 规范](https://www.rfc-editor.org/rfc/rfc792.html)

## 出现大量 TCP TIME_WAIT 的原因是什么，如何排查？

### 1. TIME_WAIT 的作用

\*\*TIME_WAIT 是 TCP 正常关闭过程中的保护状态，通常出现在主动关闭连接的一方，不固定属于客户端或服务端。\*\*双方同时关闭等情况下也可能双方进入该状态。

主动关闭方在收到对端 FIN 并发送最后的 ACK 后，保留一段时间的连接状态，主要用于：

* 如果最后一个 ACK 丢失，能够在收到对端重传的 FIN 后再次确认。
* 为旧连接的延迟报文留出消退时间，减少同一四元组被后续连接复用时的干扰。

协议描述的等待时间为 `2 × MSL`，MSL \[+MSL] 是报文的最大生存时间。实际内核实现及安全复用策略可能不同，不能直接断言所有系统都固定等待 60 秒或 4 分钟。[参考：TCP 规范 RFC 9293](https://www.rfc-editor.org/rfc/rfc9293.html)

### 2. 为什么会积累很多？

| 常见原因 | 应检查什么 |
| --- | --- |
| 请求大量使用短连接 | HTTP 连接复用、数据库连接池、RPC 客户端是否每次请求都新建连接 |
| 空闲超时过短或多层超时不一致 | 客户端、代理、负载均衡和服务端的连接关闭策略 |
| 连接池频繁创建销毁 | 最大连接数、空闲回收、最大生命周期与实例重启情况 |
| 失败重试或上游流量突增 | 建连速率、错误率、重试次数、发布与流量变化 |

在稳定负载下，可以粗略估算：`TIME_WAIT 数量 ≈ 每秒进入该状态的连接数 × 平均保留时间`。例如每秒 1000 条连接进入、平均保留 60 秒，数量就可能达到约 6 万。这只是量级示例，不是内核默认配置说明。

### 3. Linux 上的排查步骤

先确认数量、增长趋势、连接两端地址，再定位谁主动关闭：

```sh
# 查看各类 socket 的总体统计
ss -s

# 查看 TIME_WAIT 连接，-H 去掉表头，-n 保留数字地址
ss -Htan state time-wait

# 统计当前网络命名空间中的数量
ss -Htan state time-wait | wc -l

# 查看特定服务端口相关连接，例如本地 8080 端口
ss -Htan state time-wait '( sport = :8080 )'

# 查看连接计时器
ss -tanop state time-wait
```

生产排查时在目标主机或容器对应的网络命名空间执行，端口按实际业务替换。观察本地地址与对端地址：如果本地是临时端口、对端集中在数据库或上游服务端口，重点看出站连接复用；如果本地是服务监听端口，则结合入站流量与关闭策略检查。必要时抓取指定连接的 FIN / ACK，确认关闭顺序，而不是只凭端口判断主动关闭方。

TIME_WAIT 通常已没有应用持有的完整 socket 文件描述符，因此 `ss -p` 不一定能显示原进程，不能因为没有进程信息就认为它是异常残留。还需要结合连接日志、代理日志和抓包定位。[参考：ss 手册](https://man7.org/linux/man-pages/man8/ss.8.html)

随后确认是否真的造成资源或业务问题：出站连接是否出现 `Cannot assign requested address` 等临时端口分配错误，是否存在建连失败、延迟升高、NAT 端口或连接跟踪资源压力。端口约束与连接四元组、地址数量及复用规则有关，不能把所有 TIME_WAIT 简单相加后与单个端口范围比较。

### 4. 如何优化？

优先复用长连接、合理配置连接池，协调各层空闲超时，控制无效重试，避免每次请求都创建并销毁客户端。若确认是容量问题，再结合实际内核版本、流量方向和网络拓扑评估端口范围及安全复用策略。

不要把修改 `tcp_fin_timeout` 当作缩短 TIME_WAIT 的通用方法：该参数主要约束孤立连接在 FIN_WAIT_2 中的等待，与 TIME_WAIT 不同。`tcp_tw_reuse` 也有版本、时间戳与安全条件，不能照搬参数；旧的 `tcp_tw_recycle` 已从 Linux 移除，不应作为现行优化方案。[参考：Linux TCP 参数](https://www.kernel.org/doc/html/latest/networking/ip-sysctl.html)

还要区分 **CLOSE_WAIT**：它通常表示已收到对端关闭通知，但本地应用尚未完成关闭。大量持续的 CLOSE_WAIT 更应检查连接释放、异常路径和资源泄漏；TIME_WAIT 本身则通常是内核正常回收连接的一部分。

\*\*面试回答：\*\*大量 TIME_WAIT 通常来自高频短连接和主动关闭，是可靠关闭机制的结果，不一定是故障。我会用 ss 看数量趋势与连接地址，结合日志或抓包确认谁关闭、为何频繁建连，再检查端口和网络资源是否真的受限。优先优化连接复用、连接池、超时和重试，而不是直接缩短内核超时；同时与 CLOSE_WAIT 资源释放问题区分。

\[+MSL]:
MSL（Maximum Segment Lifetime，最大报文段生存时间）表示 TCP 报文段在网络中可能保留的最长时间。TIME_WAIT 的协议等待时间用 2 MSL 描述；实际系统的计时与复用策略由具体实现决定。

\*\[MVCC]: Multi-Version Concurrency Control，多版本并发控制；通过记录版本与可见性规则支持一致性读取。
\*\[ICMP]: Internet Control Message Protocol，互联网控制报文协议；用于差错报告、回显等网络层控制功能。
\*\[MSL]: Maximum Segment Lifetime，最大报文段生存时间。
