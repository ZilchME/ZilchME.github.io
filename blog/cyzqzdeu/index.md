## 秒杀系统如何保证 Redis 和数据库中库存的最终一致性

关键是把 Redis 减扣定义为预占库存，把 MySQL 定义为最终库存版本，让每一次预占都有可追踪的结果。

例如 Redis 预占 1 件库存，MySQL 库存不减扣，1 件正在处理。订单最终结果收束为两种结果：订单成功，MySQL 减扣；订单失败，Redis 回补到 100.

一个完整的闭环处理是：

1. **原子预占**：Redis Lua 同时检查库存、限购，并扣库存；以唯一 `requestId` 记录预占数量和 `PENDING` 状态。重复请求不能重复扣。
2. **可靠投递**：把该 `requestId` 的下单任务持久化到 MQ。发送结果不确定时重试并按 `requestId` 去重，不能直接认定失败并回补。
3. **数据库落单**：消费者在本地事务中按 `requestId` 幂等创建订单，并用 `库存 >= 购买数量` 的条件更新 MySQL；事务提交后才确认消费。若订单与库存在不同数据库，需要补偿流程，不能依赖一个本地事务覆盖两个服务。
4. **确认或回补**：落单成功就把预占标为完成，Redis 可售库存无需再扣一次；确定失败后，用 Lua 检查状态，确保只回补一次。超时只代表结果未知，须先查订单结果。
5. **对账兜底**：定时扫描长期 `PENDING` 的请求，结合订单和扣减记录重试或补偿。对账时应满足 **Redis 可售库存 + 未完成预占量 = MySQL 剩余库存**，不能在有请求进行时简单用 MySQL 数值覆盖 Redis。Redis 数据丢失时，应暂停放量，再依据 MySQL 和持久化的待处理请求重建。
