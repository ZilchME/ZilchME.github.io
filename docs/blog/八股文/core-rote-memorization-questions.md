## 核心八股

### 1. 描述一下TCP三次握手？为什么两次不可以？描述一下TCP四次握手？为什么三次不可以？

TCP 协议的连接管理就像一次严谨的“外交建立”与“和平分手”过程。三次握手是为了确保双方都具备通信能力并同步“暗号”（序列号），而四次挥手则是为了优雅地处理双向通道中可能残留的数据。

以下是关于这一过程的详细解析：

一、TCP 三次握手：连接的建立

三次握手的核心目的是同步双方的初始序列号（ISN），并确认双方的接收和发送能力都正常。

过程描述：

1. 第一次握手（SYN）：客户端发送一个 `SYN=1` 的报文，携带自己的初始序列号 `seq=x`。此时客户端进入 `SYN_SENT` 状态，意思是：“我想和你建立连接，我的起始编号是 x。”
2. 第二次握手（SYN + ACK）：服务器收到请求后，回复一个 `SYN=1, ACK=1` 的报文。确认号为 `ack=x+1`（表示收到了 x，期待 x+1），同时携带服务器自己的初始序列号 `seq=y`。此时服务器进入 `SYN_RCVD` 状态，意思是：“收到你的请求了，我也同意连接，我的起始编号是 y。”
3. 第三次握手（ACK）：客户端收到服务器的同意后，发送一个 `ACK=1` 的报文，确认号 `ack=y+1`，序列号 `seq=x+1`。此时客户端和服务器都进入 `ESTABLISHED` 状态，连接正式建立。

为什么两次不可以？
如果只有两次握手（即服务器发出 SYN+ACK 后就认为连接建立），会存在历史连接干扰的风险：

+ 场景：假设客户端发出的第一个 SYN 报文因网络拥堵滞留了。客户端超时重传了一个新的 SYN 并完成了数据传输，连接关闭。
+ 后果：此时，那个滞留的“旧 SYN”突然到达了服务器。如果是两次握手，服务器会误以为这是一个新请求，直接回复 SYN+ACK 并建立连接（分配资源）。但客户端并没有发起新请求，会忽略这个包。结果服务器会一直傻等，导致资源浪费。
+ 解决：三次握手强制要求客户端在第三次确认。服务器在发出 SYN+ACK 后处于“半连接”状态，如果收不到第三次 ACK，服务器超时后就会释放资源，从而避免错误建立连接。

二、TCP 四次挥手：连接的断开

四次挥手的核心目的是安全地释放双向资源，确保双方数据都发送完毕。

过程描述：

1. 第一次挥手（FIN）：主动关闭方（如客户端）发送 `FIN=1`，表示“我没有数据要发了，但我还能接收你的数据”。
2. 第二次挥手（ACK）：被动关闭方（如服务器）收到 FIN 后，回复 `ACK` 确认。此时连接处于半关闭状态。服务器可能还有数据没发完，所以先回复一个 ACK 说“收到请求，请稍等”，而不是立即关闭。
3. 第三次挥手（FIN）：服务器将剩余数据发送完毕后，发送 `FIN=1`，表示“我也没数据要发了，我也要关闭了”。
4. 第四次挥手（ACK）：客户端收到 FIN 后，回复 `ACK` 确认。服务器收到后关闭连接；客户端进入 `TIME_WAIT` 状态，等待一段时间（2MSL）确保服务器收到了 ACK 后，才彻底关闭。

为什么三次不可以？
根本原因在于 TCP 是全双工通信，两个方向的通道是独立的：

+ 数据未发完：当一方发送 FIN（请求关闭）时，只代表它不再发送数据，但它仍然可以接收数据。另一方可能还有未处理完的数据需要发送。
+ 合并的情况：因此，服务器收到 FIN 后，不能立即发送 FIN，必须先回复 ACK 进行“等待”。只有等数据真正发完了，才能发送 FIN。这就导致了第二步的 ACK 和第三步的 FIN 通常无法合并，必须分两次发送。
+ 例外：只有在服务器也没有数据要发这种特殊情况下，ACK 和 FIN 才会合并，此时挥手会变成三次，但标准流程设计必须考虑到数据未发完的情况，所以是四次。

三、关键差异总结

| 机制 | 核心目的 | 步骤拆分原因 |
| :--- | :--- | :--- |
| 三次握手 | 建立双向通信能力 | 防止历史失效的连接请求导致服务器资源浪费；确保双方收发能力正常。 |
| 四次挥手 | 安全释放双向资源 | 全双工特性导致关闭需分方向进行；被动方可能需时间处理剩余数据，ACK 与 FIN 需分开。 |

### 2. 操作系统里进程和线程的区别？为什么线程切换消耗更小？

在操作系统中，进程和线程的核心区别在于资源所有权和调度单位的不同。简单来说，进程是资源分配的基本单位，而线程是CPU调度和执行的基本单位。

一个进程就像一个拥有独立办公室、设备和资料的“项目组”，它拥有独立的内存空间（代码段、数据段、堆等）和系统资源（如文件句柄）。而线程则是项目组内的“员工”，一个进程可以包含多个线程，这些线程共享项目组的所有资源（办公室、资料等），但每个线程都有自己独立的“工作台”（栈空间）和“当前任务进度”（寄存器和程序计数器）。

一、为什么线程切换消耗更小？

线程切换的开销远小于进程切换，核心原因在于切换时需要保存和恢复的上下文信息量不同，这直接导致了两个关键差异：

1. 无需切换虚拟内存空间

+ 进程切换：由于每个进程都有自己独立的虚拟地址空间，从一个进程切换到另一个进程时，CPU必须切换整个内存上下文。这包括加载新进程的页表、刷新转换后备缓冲区（TLB）和使CPU高速缓存（Cache）失效。这是一个非常耗时的“重量级”操作。
+ 线程切换：同一进程内的所有线程共享同一块虚拟内存空间。因此，在线程之间切换时，CPU的内存管理单元（MMU）无需改变，TLB和Cache也得以保留，省去了最昂贵的一部分开销。

1. 需要保存的上下文信息更少

+ 进程切换：需要保存和恢复整个进程的“家当”，包括完整的寄存器状态、内核堆栈、打开的文件描述符、信号处理函数等所有资源的状态。
+ 线程切换：只需要保存和恢复线程私有的少量信息，主要是程序计数器（PC）、栈指针（SP）和一组通用寄存器的值。这就像只是换了一个人坐在同一个工作台前继续工作，而不是把整个办公室的东西都搬走再换一批新的进来。

二、进程与线程核心区别对比

| 特性 | 进程 (Process) | 线程 (Thread) |
| :--- | :--- | :--- |
| 基本单位 | 资源分配的基本单位 | CPU调度的基本单位 |
| 内存空间 | 拥有独立的虚拟地址空间 | 共享所属进程的地址空间 |
| 切换开销 | 大（需切换内存空间、页表等） | 小（仅切换寄存器和栈等） |
| 通信方式 | 复杂，需使用IPC机制（如管道、消息队列） | 简单，可直接读写共享内存 |
| 可靠性 | 高，一个进程崩溃不影响其他进程 | 低，一个线程崩溃可能导致整个进程崩溃 |

### 3. Runnable和Callable接口有什么区别？

`Runnable` 和 `Callable` 都是 Java 中用于定义任务的接口，但它们在设计目标和能力上有本质区别。`Callable` 可以看作是 `Runnable` 的功能增强版，主要区别体现在以下三个方面：

一、返回值

+ Runnable: 其 `run()` 方法没有返回值（返回 `void`），适用于执行完即结束、无需反馈结果的任务，例如记录日志或发送通知。
+ Callable: 其 `call()` 方法可以返回一个泛型类型的结果。任务执行完毕后，可以通过 `Future` 对象获取这个返回值，适用于需要异步计算并返回结果的场景。

二、异常处理

+ Runnable: `run()` 方法不能向外抛出受检异常（Checked Exception），任何异常都必须在方法内部通过 `try-catch` 处理，否则会导致编译错误。
+ Callable: `call()` 方法明确声明 `throws Exception`，允许将任务执行过程中的受检异常向上抛出。调用方可以通过 `Future.get()` 方法捕获到封装在 `ExecutionException` 中的原始异常。

三、使用方式

+ Runnable: 使用方式更灵活，既可以通过 `new Thread(runnable).start()` 直接启动线程，也可以提交给线程池（`ExecutorService`）执行。
+ Callable: 无法直接用于创建 `Thread`，必须提交给线程池（`ExecutorService.submit()`）执行。提交后会返回一个 `Future` 对象，用于管理任务状态、获取结果或取消任务。

### 4. zset的具体底层实现原理是什么？

Redis 的 ZSet（有序集合）底层实现非常巧妙，它并非单一的数据结构，而是根据数据量的大小和元素内容的长度，在压缩列表（ziplist）和跳表+字典（skiplist + dict）之间进行动态切换，以在内存占用和操作效率之间取得最佳平衡。

一、两种底层实现结构

1. 压缩列表（ziplist）：为小数据量而生
当 ZSet 中的元素数量较少（默认 ≤ 128个）且每个元素的字符串长度也较短（默认 ≤ 64字节）时，Redis 会使用压缩列表。

+ 原理：压缩列表是一块连续的内存空间，数据按顺序紧凑地存储，形式为 `[成员1][分值1][成员2][分值2]...`。
+ 优点：内存占用极小，没有多余的指针开销，且对 CPU 缓存非常友好。
+ 缺点：由于是连续内存，增删操作可能涉及大量内存移动，时间复杂度为 O(N)，不适合大数据量。

1. 跳表 + 字典（skiplist + dict）：为大数据量设计
一旦数据量或元素大小超过上述阈值，ZSet 就会自动转换为跳表和字典的组合结构。

+ 字典（dict）：维护了一个从 `member`（成员）到 `score`（分值）的哈希映射。这使得查找单个成员的分数（`ZSCORE` 命令）可以达到 O(1) 的时间复杂度。
+ 跳表（skiplist）：一种多层索引的有序链表，它按照 `score` 从小到大对所有成员进行排序。跳表使得插入、删除和范围查询（如 `ZRANGE`）等操作的平均时间复杂度为 O(logN)，效率非常高。

二、Redis 7.0 的重要变更

值得注意的是，从 Redis 7.0 版本开始，ZSet 的底层实现统一采用了 `skiplist + dict` 结构，取消了`ziplist`编码。这一变更旨在简化实现并提升在大数据量场景下的性能稳定性。

三、为什么选择跳表（SkipList）？

Redis 选择跳表而非红黑树等其他平衡树结构，主要基于以下几点工程考量：

+ 实现更简单：跳表的实现代码远比红黑树等平衡树简洁，调试和维护成本更低。
+ 范围查询更高效：跳表本质上是有序的链表，进行范围查询时可以直接顺序遍历，非常高效。而平衡树需要进行中序遍历，相对繁琐。
+ 并发友好：跳表的插入和删除操作只涉及局部节点的指针修改，更容易实现无锁（lock-free）的并发优化。

总而言之，ZSet 通过这种混合数据结构的设计，既能在数据量小时极致节省内存，又能在数据量大时保证高效的增删改查性能。

### 5. 发生Full GC的常见原因有哪些？

Full GC（全局垃圾回收）是 JVM 中代价高昂的操作，因为它会暂停所有应用线程（Stop-The-World），严重影响系统性能。其发生的核心原因通常是老年代或元空间的内存回收速度跟不上对象的分配和晋升速度。

一、老年代空间不足

这是最常见的 Full GC 触发原因。当老年代（Old Generation）没有足够的空间容纳新晋升的对象时，就会触发 Full GC。具体场景包括：

1. 对象正常晋升：新生代中经过多次 Minor GC 后依然存活的对象，其年龄达到阈值（默认为15）后会晋升到老年代。如果老年代空间不足，便会触发 Full GC。
2. 大对象直接进入：程序中创建的大数组、大字符串等对象，会绕过新生代，直接在老年代分配。如果老年代剩余空间不足以容纳这个大对象，就会立即触发 Full GC。
3. 动态年龄判断：即使对象年龄未达到阈值，但如果 Survivor 区中同一年龄段的所有对象总大小超过了 Survivor 区的一半，这些对象也会提前晋升到老年代，可能导致老年代空间不足。

二、内存泄漏

内存泄漏是导致 Full GC 频繁发生且回收效果不佳的“隐形杀手”。它指的是程序中已经不再使用的对象，由于被某些不合理的引用长期持有，导致垃圾回收器无法回收它们。这些“僵尸”对象会持续占据老年代空间，最终耗尽内存并引发频繁的 Full GC，甚至 `OutOfMemoryError`。常见的泄漏点包括静态集合（如 `static Map`）无限制地添加元素、`ThreadLocal` 使用后未清理等。

三、元空间（Metaspace）耗尽

元空间用于存储类的元数据、常量池等信息。当应用程序频繁动态加载类（例如使用反射、CGLIB 动态代理、OSGi 等），或者存在类加载器泄漏时，元空间会被迅速填满。一旦元空间使用量达到其阈值（由 `-XX:MetaspaceSize` 等参数控制），JVM 就会触发 Full GC 来尝试回收无用的类元数据。

四、其他常见原因

+ 显式调用：在代码中直接调用了 `System.gc()` 或 `Runtime.getRuntime().gc()`，这会“建议”JVM 执行一次 Full GC。通常可以通过 JVM 参数 `-XX:+DisableExplicitGC` 来禁用此行为。
+ GC 策略退化：在使用 CMS 或 G1 等并发回收器时，如果并发回收的速度跟不上对象分配的速度，或者老年代内存碎片过多导致无法分配连续空间，回收器会退化为串行的 Full GC 来整理整个堆。

### 6. 介绍一下常见的http状态码？

HTTP 状态码是服务器对客户端请求的“暗号”，由三位数字组成。它的核心逻辑在于首位数字，这决定了请求是成功、失败还是需要进一步操作。我们可以将这些状态码分为五大类，理解它们能帮你快速定位是“客户端的问题”还是“服务器的锅”。

一、2xx 成功：请求处理顺利

这类状态码表示服务器成功接收并处理了请求，是开发中最希望看到的结果。

+ 200 OK：最通用的成功标志，表示请求一切正常，服务器返回了请求的资源（如网页、JSON数据）。
+ 201 Created：通常用于 POST 请求，表示资源已成功创建（如注册新用户）。
+ 204 No Content：表示服务器处理成功，但响应体中没有内容（常用于 DELETE 删除操作）。

二、3xx 重定向：需要换个地方找

这类代码告诉客户端：“你要的东西不在这里，去别处拿”。

+ 301 Moved Permanently：永久重定向。资源已搬家，搜索引擎会更新索引，浏览器也会缓存新地址。
+ 302 Found：临时重定向。资源只是暂时换个位置，下次还得来老地方找。
+ 304 Not Modified：缓存神器。表示资源自上次请求后未修改，客户端可以直接使用本地缓存，无需重新下载，极大节省带宽。

三、4xx 客户端错误：你的请求有问题

这类状态码意味着服务器无法处理请求，通常是客户端（浏览器或开发者）的锅。

+ 400 Bad Request：服务器“听不懂”你的语法，通常是参数错误或报文格式有误。
+ 401 Unauthorized：未登录。请求需要身份验证（如未带 Token），服务器拒绝了请求。
+ 403 Forbidden：已登录但无权限。服务器识别了你的身份，但你没有访问该资源的资格。
+ 404 Not Found：资源不存在。服务器找不到你请求的页面或接口，这是最常见的错误之一。

四、5xx 服务器错误：服务器崩了

这类代码表示服务器在处理合法请求时内部发生了错误，通常是后端代码或运维的问题。

+ 500 Internal Server Error：万能报错。服务器遇到了意料之外的错误（如代码空指针异常），无法完成请求。
+ 502 Bad Gateway：网关报错。作为网关或代理的服务器（如 Nginx），从上游应用服务器（如 Tomcat/PHP-FPM）收到了无效响应，通常是后端服务挂了。
+ 503 Service Unavailable：服务过载。服务器暂时无法处理请求，通常是因为停机维护或流量超载。
+ 504 Gateway Timeout：网关超时。网关等待上游服务器响应的时间过长，通常是后端处理太慢（如慢 SQL）。

五、核心状态码速查表

| 状态码 | 含义 | 常见场景 |
| :--- | :--- | :--- |
| 200 | 成功 | 正常访问网页、API 返回数据 |
| 301 | 永久重定向 | 网站改版换域名、HTTP 强制跳转 HTTPS |
| 304 | 未修改 | 浏览器读取缓存，不消耗流量 |
| 400 | 错误请求 | 前端传参格式错误、缺少必填字段 |
| 401 | 未授权 | 用户未登录、Token 过期或缺失 |
| 403 | 禁止访问 | 普通用户试图访问管理员后台 |
| 404 | 未找到 | 输入了错误的网址、资源被删除 |
| 500 | 服务器内部错误 | 后端代码抛出异常、配置文件错误 |
| 502 | 网关错误 | 后端服务未启动、防火墙拦截 |
| 503 | 服务不可用 | 服务器过载、系统维护中 |

### 7. 介绍一下linux常用指令？看日志的时候会用哪些？

Linux 命令繁多，但在日常开发和运维中，核心指令其实非常集中。针对你的需求，我将重点分为“看日志”和“常用基础”两个部分来概括。

一、看日志的“三板斧”

在 Linux 中排查问题，90% 的时间都在和日志打交道。以下是最高频的命令组合：

1. 实时监控：`tail`
这是最常用的命令。当你部署完服务，需要看着控制台输出排查报错时，必须用它。

+ `tail -f filename`：实时显示文件末尾的内容，日志每增加一行，屏幕就刷新一行。
+ `tail -100f filename`：先看最后 100 行，然后开启实时跟踪。
+ 组合技：`tail -f app.log | grep "ERROR"` —— 只实时显示包含 "ERROR" 的日志，过滤掉无关信息，非常高效。

1. 全文搜索：`grep`
当日志文件巨大（几百兆甚至几个 G），你不能肉眼看，需要用 `grep` 筛选。

+ `grep "Exception" app.log`：找出所有包含 "Exception" 的行。
+ `grep -C 5 "Exception" app.log`：不仅显示报错行，还显示报错前后的 5 行（Context），帮你还原上下文。

1. 翻页查看：`less`
如果文件太大，用 `cat` 会刷屏，用 `vim` 会加载很久。`less` 是最好的选择，它只加载当前屏幕内容。

### 8. 说一下CAS存在的常见问题？

CAS（Compare-And-Swap，比较并交换）虽然是实现无锁并发、提升性能的神器（比如 `AtomicInteger` 的底层），但它并不是完美的。在实际应用中，CAS 主要面临以下三个核心问题，理解这些问题对于写出高性能的并发代码至关重要。

1. ABA 问题：被“伪装”的修改

这是 CAS 最经典、也最容易被忽视的逻辑漏洞。

+ 现象：假设线程 1 读取内存中的值为 A，准备执行 CAS 操作。但在它执行之前，线程 2 插了一脚，先把值从 A 改成了 B，紧接着又把值从 B 改回了 A。
+ 后果：当线程 1 终于执行 CAS 时，它发现内存里的值依然是 A（和它预期的一样），于是 CAS 成功执行。线程 1 以为数据从未被修改过，但实际上中间已经发生了“惊心动魄”的变化。在涉及链表操作或状态机流转时，这种“假象”可能导致严重的数据不一致。
+ 解决方案：引入版本号机制。在变量旁边加一个版本号（Stamp），每次修改变量，版本号就加 1。CAS 操作时，不仅要比较值（A 是否等于 A），还要比较版本号（1 是否等于 1）。Java 中的 `AtomicStampedReference` 就是为了解决这个问题。

1. 循环时间长，开销大（自旋开销）

CAS 是一种“乐观”策略，它假设冲突很少发生，所以不阻塞线程，而是让线程“自旋”重试。

+ 现象：在高并发场景下，如果多个线程同时争抢同一个变量的修改权，必然只有一个线程能成功，其他线程都会失败。
+ 后果：失败的线程不会挂起（像锁那样），而是进入一个死循环（`while(true)`），不断尝试再次 CAS，直到成功为止。如果竞争非常激烈，线程会长时间占用 CPU 资源进行无效的重试，导致 CPU 使用率飙升，反而降低了系统的整体吞吐量。
+ 解决方案：

+ 限制自旋次数。
+ 使用带有退避策略的自旋（失败后等待一小段时间再试）。
+ 在竞争极度激烈时，退化为使用锁（如 `synchronized`）。
+ 使用 `LongAdder` 等分段累加器来减少热点竞争。

1. 只能保证单个共享变量的原子操作

CAS 的硬件指令（如 x86 的 `cmpxchg`）通常只能针对一个内存地址进行操作。

+ 现象：如果你需要同时更新两个或多个变量，并且保证它们作为一个整体是原子的（要么都成功，要么都失败），单纯的 CAS 就无能为力了。
+ 后果：例如，你需要同时更新账户的“余额”和“积分”，如果只用 CAS 分别更新，可能会出现余额扣了但积分没加上的中间状态。
+ 解决方案：

+ 加锁：使用 `synchronized` 或 `ReentrantLock` 将多个变量包裹起来。
+ 封装对象：将多个变量封装成一个对象，然后使用 `AtomicReference` 对这个对象引用进行 CAS 操作。

核心问题总结

| 问题 | 核心痛点 | 典型解决方案 |
| :--- | :--- | :--- |
| ABA 问题 | 值没变，但过程变了（逻辑漏洞） | `AtomicStampedReference`<br/>（加版本号） |
| 自旋开销 | 竞争激烈时 CPU 占用过高（性能损耗） | 限制重试次数、退避策略、`LongAdder` |
| 单变量限制 | 无法原子地更新多个变量（功能局限） | 使用锁、`AtomicReference`<br/> 封装对象 |

### 9. 能作为gc roots的对象是什么？

在Java中，GC Roots是垃圾回收的根对象集合，是可达性分析算法中判断对象是否存活的起始点。能作为GC Roots的对象主要包括以下几类：

+ 虚拟机栈中引用的对象（如方法内的局部变量）；
+ 方法区中静态属性引用的对象（如类的静态变量）；
+ 方法区中常量引用的对象（如字符串常量池中的引用）；
+ 本地方法栈中JNI引用的对象（Native方法引用的对象）；
+ Java虚拟机内部的引用（如基本类型对应的Class对象、系统类加载器等）；
+ 被同步锁持有的对象（如`synchronized`持有的对象）。

这些根对象及其引用链上的所有对象不会被回收，而其他不可达的对象则会被标记为可回收。

### 10. 介绍一下慢查询sql的排查思路？

慢 SQL 排查的核心思路可以概括为：先定位、再分析、后优化。这是一个系统性的工程，旨在精准找到性能瓶颈，而非盲目修改。

第一步：定位慢 SQL

优化的前提是找到真正影响性能的 SQL 语句。主要有两种核心手段：

1. 慢查询日志 (Slow Query Log)
这是最直接有效的方法。通过开启 MySQL 的慢查询日志，可以将所有执行时间超过设定阈值（`long_query_time`，通常设为 1 秒）的 SQL 记录下来。这是定位线上问题的第一手资料。
2. 实时监控工具
对于正在发生的性能抖动，可以使用 `SHOW PROCESSLIST` 命令查看当前正在执行的线程，或使用 `performance_schema` / `sys` 库来查询历史和高频的慢 SQL。此外，APM 全链路监控工具（如 SkyWalking）也能从应用层面关联并定位到具体的慢 SQL。

第二步：分析执行计划

找到慢 SQL 后，切忌凭感觉修改。必须使用 `EXPLAIN` 命令来分析其执行计划，这是诊断问题的核心抓手。通过分析 `EXPLAIN` 的结果，可以洞察 MySQL 优化器是如何执行这条 SQL 的。重点关注以下字段：

+ `type`: 访问类型，反映了查询的效率。性能从优到劣依次为 `system` > `const` > `eq_ref` > `ref` > `range` > `index` > `ALL`。出现 `ALL`（全表扫描）是必须优化的强烈信号。
+ `key`: 实际使用的索引。如果为 `NULL`，则说明没有使用任何索引。
+ `rows`: 预估需要扫描的行数。这个值越小越好，如果远大于实际返回的行数，则说明效率低下。
+ `Extra`: 额外信息。如果出现 `Using filesort`（需要额外排序）或 `Using temporary`（使用了临时表），通常意味着 SQL 有较大的优化空间。

第三步：针对性优化

根据执行计划分析出的瓶颈，进行精准优化，主要方向包括：

+ 索引优化：这是最常见的优化手段。例如，为 `WHERE`、`ORDER BY`、`JOIN` 的字段创建合适的索引，但要避免在索引列上进行函数运算或隐式类型转换，这会导致索引失效。
+ SQL 语句改写：优化 SQL 写法，例如避免使用 `SELECT *`，只查询必要字段；用 `JOIN` 替代子查询；对深度分页进行优化等。
+ 表结构与架构调整：在更宏观的层面，可以考虑优化表结构（如选择合适的数据类型）、进行分库分表，或引入缓存来减轻数据库压力。

### 11. 对比一下CMS和G1垃圾回收器？

CMS（Concurrent Mark-Sweep）和 G1（Garbage-First）是两款代际不同、设计哲学迥异的垃圾回收器。简单来说，G1 是为了解决 CMS 在大内存和碎片化问题上的局限性而诞生的，旨在提供更可控的停顿时间和更高的整体效率。

一、设计目标与停顿时间

+ CMS: 核心目标是追求最短的停顿时间。它通过让垃圾回收线程与用户线程并发工作，来降低 GC 对应用响应时间的影响。然而，这种停顿时间是不可预测的，在发生 `Concurrent Mode Failure` 或需要处理内存碎片时，会退化为长时间的串行 Full GC，导致严重的停顿。
+ G1: 核心目标是实现可预测的停顿时间。它允许用户通过参数（如 `-XX:MaxGCPauseMillis`）设定期望的停顿目标，G1 会根据这个目标动态调整每次回收的内存区域大小，从而在延迟和吞吐量之间取得平衡。

二、内存布局与回收算法

+ CMS: 采用传统的固定分代模型，将堆内存物理上划分为新生代和老年代。它使用标记-清除（Mark-Sweep）算法，这个算法不会整理内存，长期运行后会产生大量内存碎片，当碎片过多导致无法为大对象分配连续空间时，便会触发 Full GC。
+ G1: 采用创新的分区（Region）模型，将堆内存划分为多个大小相等的独立区域（Region），这些区域可以动态地扮演新生代、老年代等角色。它整体采用标记-整理（Mark-Compact）和局部复制（Copying）算法，在回收时会自动整理存活对象，从根本上避免了内存碎片的产生。

三、适用场景与现状

+ CMS: 在 JDK 9 中已被标记为废弃，并在 JDK 14 中被正式移除。它适用于 JDK 8 及更早版本中，堆内存较小（通常小于 4GB）、对延迟敏感且对象生命周期分布较简单的应用。
+ G1: 自 JDK 9 起成为默认的垃圾回收器。它特别适合大内存（6GB以上）、多核处理器的服务器端应用，尤其是在需要兼顾低延迟和高吞吐量的场景下，G1 是更全面和现代化的选择。

### 12. 为什么普通的快照读不需要加锁？

普通的快照读（如MySQL的默认SELECT）不需要加锁，主要依赖于多版本并发控制（MVCC）机制。

事务在启动时会生成一个一致性视图，读操作通过读取该视图下的数据快照（由undo日志构建的历史版本）来保证数据一致性，从而避免了脏读、不可重复读等问题。由于读操作不直接访问当前数据页，而是访问历史版本，因此无需加锁即可实现读写并发，大幅提升了系统吞吐量。

### 13. java线程和os线程的区别？

简单来说，在现代 Java 开发中（JDK 1.2 以后），Java 线程和操作系统（OS）线程在本质上是“一对一”的映射关系。你可以把 Java 线程看作是操作系统线程在 JVM 层面的一个“高级代理”或“逻辑包装”。

虽然它们底层紧密绑定，但在抽象层次、管理方式和特性上存在显著区别。以下是核心差异的概括：

一、抽象层次：逻辑包装 vs 物理实体

+ Java 线程：是 JVM 层面的逻辑抽象。它不仅仅包含底层的执行能力，还维护了许多 Java 特有的属性，如线程优先级（1-10）、中断状态、线程局部变量（ThreadLocal）以及 Java 定义的线程状态（如 NEW, BLOCKED, WAITING 等）。
+ OS 线程：是操作系统内核调度的物理实体（通常对应内核线程）。它由操作系统内核管理，拥有独立的内核栈、程序计数器和寄存器状态，是 CPU 调度的基本单位。

二、调度与管理：建议 vs 决策

+ 调度权归属：Java 线程的调度最终依赖于操作系统。当你调用 `Thread.start()` 时，JVM 会通过系统调用（如 Linux 下的 `pthread_create`）请求操作系统创建一个内核线程。
+ 优先级的差异：Java 线程的优先级（1-10）仅仅是对操作系统的一个“建议”。JVM 会将这些优先级映射到操作系统的优先级上（例如 Linux 的 nice 值或 Windows 的优先级类），但操作系统拥有最终决定权，可能会忽略 Java 的优先级设置，或者不同操作系统对优先级的映射规则不同。

三、跨平台性：屏蔽差异

+ Java 线程：提供了统一的 API（`java.lang.Thread`），屏蔽了底层操作系统的差异。无论你的代码运行在 Windows、Linux 还是 macOS 上，Java 线程的创建和使用方式都是一致的。
+ OS 线程：不同操作系统的线程实现机制（如 Windows 的 Win32 线程 API 和 Linux 的 POSIX threads/pthread）和调度策略各不相同。Java 线程的存在让开发者无需关心这些底层细节。

四、核心差异对比表

| 对比维度 | Java 线程 | 操作系统线程 |
| :--- | :--- | :--- |
| 本质定位 | JVM 层面的逻辑封装，包含 Java 特有状态 | 内核调度的物理实体，CPU 调度的基本单位 |
| 管理主体 | JVM 负责生命周期管理（创建/销毁对象） | 操作系统内核负责实际调度与资源分配 |
| 调度策略 | 优先级仅为“建议”，最终由 OS 决定 | 基于时间片轮转、优先级抢占等内核策略 |
| 跨平台性 | 强，API 统一，与 OS 无关 | 弱，依赖特定 OS 的 API（如 pthread） |
| 资源开销 | 相对轻量（但在 1:1 模型下仍受限于 OS） | 重量级，创建和切换涉及用户态/内核态转换 |

### 14. 具体说一下协程？为什么有了线程还要用协程？

要理解协程，一个很形象的比喻是：如果线程是操作系统直接管理的“正式员工”，那么协程就是公司内部自行调度的“轻量级任务包”。

一、什么是协程？

协程本质上是一种用户态的轻量级线程。它最核心的特征是，其创建、调度和切换完全由程序自身（或语言运行时）在用户空间管理，而不需要操作系统内核的介入。这使得协程拥有两个关键能力：

1. 可挂起与恢复：协程可以在执行过程中主动“暂停”（挂起），保存当前的执行状态，然后在稍后的某个时刻从暂停的地方“恢复”执行。
2. 极低的开销：由于不涉及内核态切换，协程的上下文切换成本极低，通常只在纳秒级别。

二、为什么有了线程还需要协程？

引入协程主要是为了解决传统线程在高并发场景下的两大痛点：重量级和高切换成本。

1. 内存占用更小

+ 线程：每个线程都需要操作系统分配一块独立的栈空间，默认大小通常在 1MB 左右。当需要处理成千上万个并发任务时（例如一个服务器要维持10万个长连接），仅栈内存就可能消耗上百GB，导致内存耗尽（OOM）。
+ 协程：协程的栈空间非常小，通常只有几 KB（例如Go语言的Goroutine初始栈仅为2KB），并且可以动态伸缩。这使得单机轻松创建数十万甚至上百万个协程成为可能。

1. 上下文切换更快

+ 线程切换：线程的调度由操作系统内核负责。切换时，CPU需要从用户态陷入内核态，保存和恢复完整的寄存器、程序计数器、栈指针以及页表等信息，这个过程耗时在微秒级。在高并发下，大量的CPU时间会被浪费在线程切换上。
+ 协程切换：协程的切换完全在用户态完成，不涉及内核态。它只需要保存和恢复极少量的寄存器状态，耗时仅在纳秒级，比线程切换快了几个数量级。

三、核心区别与适用场景

| 特性 | 线程 (Thread) | 协程 (Coroutine) |
| :--- | :--- | :--- |
| 调度者 | 操作系统内核 | 用户程序（运行时） |
| 切换成本 | 高（微秒级） | 极低（纳秒级） |
| 栈内存 | MB级 | KB级 |
| 并行能力 | 多核并行 | 单线程内并发，需配合多线程实现多核并行 |

适用场景：

+ 协程的“绝对主场”：I/O密集型任务。例如网络服务、Web服务器、数据库访问等。在这些场景中，任务大部分时间都在等待I/O操作完成，使用协程可以在等待时迅速切换到其他任务，极大地提升CPU利用率和系统吞吐量。
+ 线程的适用场景：CPU密集型任务。例如复杂的数学计算、图像处理等。这类任务需要持续占用CPU，协程的“暂停-恢复”优势无法发挥，反而可能因为协作式调度不当导致其他任务“饿死”。

总而言之，协程通过牺牲一些隔离性和并行能力，换取了极致的轻量和高并发性能，是构建现代高并发、高吞吐网络服务的基石。

### 15. 抽象类与接口的区别？

抽象类和接口是 Java 中实现抽象的两种核心机制，它们最本质的区别在于设计哲学：抽象类是对“是什么”（is-a）的抽象，用于构建类族的通用模板；而接口是对“能做什么”（can-do）的抽象，用于定义跨类别的行为契约。

一、设计哲学：身份模板 vs 行为契约

+ 抽象类 (Abstract Class)：它像一个不完整的蓝图，定义了一组相关类的核心身份和共性。例如，一个 `Animal` 抽象类可以包含所有动物共有的属性（如 `name`）和行为（如 `sleep()`），同时强制子类去实现各自特有的行为（如 `makeSound()`）。它强调的是代码复用和层级关系。
+ 接口 (Interface)：它像一份能力说明书或一份合同，定义了一系列行为规范。任何类，无论它在继承树中的位置如何，只要实现了这个接口，就承诺具备相应的能力。例如，`Flyable` 接口可以被 `Bird`、`Airplane` 等完全不同的类实现。它强调的是解耦和功能的扩展。

二、语法与实现差异

从语法层面看，两者在继承、成员和方法实现上有着严格的区别：

| 对比维度 | 抽象类 (Abstract Class) | 接口 (Interface) |
| :--- | :--- | :--- |
| 继承/实现 | 单继承：一个类只能继承一个抽象类。 | 多实现：一个类可以实现多个接口。 |
| 成员变量 | 可以是任意类型的变量（实例变量、常量），用于存储对象的状态。 | 只能是 `public static final`<br/> 常量（Java 9+ 支持私有静态常量），不存储状态。 |
| 构造器 | 有构造器：供子类继承时调用，用于初始化共有的状态。 | 无构造器：因为接口不定义状态，无需初始化。 |
| 方法实现 | 可包含抽象方法（强制子类实现）和具体方法（提供默认实现）。 | Java 8 之前只有抽象方法；Java 8+ 支持 `default`<br/> 和 `static`<br/> 方法；Java 9+ 支持 `private`<br/> 方法。 |
| 访问权限 | 方法和属性可以使用 `private`<br/>、`protected`<br/>、`public`<br/> 等任意修饰符。 | 方法默认是 `public`<br/>，Java 9+ 的私有方法仅用于内部逻辑复用。 |

三、演进与选择建议

随着 Java 版本的演进（特别是 Java 8 引入 `default` 方法），接口的功能得到了增强，使得两者界限在某些场景下变得模糊。但在实际开发中，选择的原则依然清晰：

+ 优先选择接口：当你需要定义一种能力，让多个不相关的类都能具备时；当你需要实现多重继承的效果时；当你希望 API 能够向后兼容地扩展时（利用 `default` 方法）。
+ 选择抽象类：当你需要为一系列紧密相关的类共享代码（包括字段和具体方法）时；当你需要控制子类的访问权限（如使用 `protected` 成员）时；当你需要定义一个不可变的模板方法模式时。

### 16. 为什么垃圾回收时的STW的时间有时候不可控？与选择的垃圾回收器有什么关系？

垃圾回收（GC）时的“世界暂停”（STW）时间之所以有时不可控，其根本原因在于保证内存数据一致性的需求与应用程序运行状态之间的矛盾。

为了准确识别和回收垃圾对象，垃圾回收器必须在某些关键阶段（如标记存活对象、移动对象）确保堆内存中的对象引用关系是静止不变的。如果用户线程在此期间修改了对象图，GC 就可能误判，导致程序错误。因此，JVM 必须暂停所有应用线程，即触发 STW。

STW 时间的长短与所选的垃圾回收器及其算法直接相关，不同回收器的设计目标决定了其 STW 的可控性。

一、为什么 STW 时间不可控？

即使在现代并发回收器中，STW 也无法完全消除，其时间受多种动态因素影响，导致难以精确预测：

1. 堆内存大小与对象数量：这是最直接的因素。堆越大、存活对象越多，GC 需要扫描和处理的内存范围就越广，即使是并发的标记阶段，其初始和最终的 STW 阶段耗时也会随之增长。
2. 对象存活率：如果老年代中大部分对象都是存活的（高存活率），那么在标记和整理（压缩）阶段就需要处理海量数据，这会显著增加 STW 的时间，尤其是对于使用“标记-整理”算法的回收器。
3. 引用关系复杂度：对象之间的引用关系越复杂、层级越深，GC Roots 的遍历和对象图的标记过程就越耗时。
4. 应用线程行为：在并发标记阶段，应用线程会持续创建新对象或修改引用。为了修正这些变化带来的“漏标”问题，回收器需要在“重新标记”阶段进行 STW 来统一处理，这个阶段的时间取决于应用线程修改引用的频率和数量。

二、与垃圾回收器的关系

垃圾回收器的演进史，本质上就是一部不断降低和优化 STW 时间的历史。不同的回收器通过不同的算法和策略，在 STW 的可控性上表现出巨大差异。

| 回收器类型 | STW 特点 | 可控性分析 |
| :--- | :--- | :--- |
| Serial / Parallel | 完全 STW | 不可控。整个 GC 过程（包括新生代和老年代回收）都会暂停所有应用线程。停顿时间长，且随堆大小线性增长。 |
| CMS | 部分并发，两次短暂 STW | 相对可控，但有风险。它在初始标记和重新标记阶段会 STW，时间较短。但在内存碎片过多或并发清理失败时，会退化为 Serial Old，导致长时间且不可控的 STW。 |
| G1 | 多次短暂 STW，目标可控 | 高度可控。它将堆划分为多个 Region，并允许用户设定最大停顿时间目标（`-XX:MaxGCPauseMillis`<br/>）。G1 会根据历史数据，选择回收价值最高的 Region 集合进行回收，以在目标时间内完成。 |
| ZGC / Shenandoah | 几乎全并发，STW 极短 | 超低延迟，高度可控。它们通过读屏障、染色指针等先进技术，将几乎所有 GC 工作（包括对象移动）都与应用线程并发执行，将 STW 时间控制在 10ms 以内，且不随堆大小增长而显著增加。 |

总而言之，STW 的不可控性源于 GC 算法对内存一致性的要求以及运行时的动态变化。而选择不同的垃圾回收器，就是在选择不同的 STW 控制策略：从早期回收器的完全不可控停顿，到 G1 的可预测停顿，再到 ZGC 的亚毫秒级停顿，开发者可以根据应用对延迟的敏感度来做出最合适的选择。

### 17. G1和ZGC垃圾回收器的主要区别是什么？

G1 和 ZGC 是两款设计目标和技术实现截然不同的垃圾回收器，它们的主要区别体现在以下几个方面：

一、设计目标不同

+ G1 (Garbage-First)：旨在平衡吞吐量与延迟。它适用于堆内存较大（通常在 6GB 以上）且对停顿时间有可预测要求的应用。G1 允许用户通过参数（如 `-XX:MaxGCPauseMillis`）设定一个期望的停顿时间目标，并尽力在此范围内完成垃圾回收。
+ ZGC (Z Garbage Collector)：追求极致的低延迟。它的核心目标是无论堆内存多大（从几百 MB 到数 TB），都能将 GC 停顿时间控制在亚毫秒级（通常小于 10ms），且停顿时间不会随堆的增大而显著增加。

二、核心技术与算法不同

+ G1：将堆内存划分为多个大小固定的 Region，采用标记-整理和复制算法。它通过并发标记来减少停顿，但在部分阶段（如初始标记、最终标记）仍需暂停所有应用线程（STW），并通过整理存活对象来避免内存碎片。
+ ZGC：采用了更先进的技术，如染色指针（Colored Pointers）和读屏障（Read Barrier）。这使得 ZGC 几乎所有的 GC 工作（包括标记、转移、重映射）都能与应用程序线程并发执行，只有极短暂的停顿用于阶段切换，从而实现了超低延迟。

三、适用场景与资源开销不同

+ G1：是 JDK 9 及之后版本的默认回收器，普适性强，适合大多数中大型服务端应用。它在延迟和吞吐量之间取得了良好平衡，但在处理超大堆（如超过 64GB）时，停顿时间可能会变长。
+ ZGC：专为超大堆（TB 级别）和极低延迟的苛刻场景设计，如金融交易、实时计算等。其代价是需要更高的 CPU 开销和额外的内存开销（用于读屏障和染色指针等），在小内存应用中性价比不高。

### 18. Sychronized和Reentrantlock有什么区别？

`synchronized` 和 `ReentrantLock` 都是 Java 中用于实现线程同步、保证线程安全的核心机制，且都支持可重入。但它们的根本区别在于：`synchronized` 是 JVM 层面的隐式锁，由 JVM 自动管理加锁与解锁；而 `ReentrantLock` 是 JDK 层面的显式锁，需要开发者手动控制，因此提供了更灵活、更强大的并发控制能力。

一、实现与使用方式

+ `synchronized`：作为 Java 的关键字，它的实现依赖于 JVM 内置的监视器锁（Monitor）。使用上非常简洁，当线程进入 `synchronized` 代码块或方法时自动加锁，执行完毕或抛出异常时自动释放，无需手动干预，有效避免了忘记释放锁导致的死锁风险。
+ `ReentrantLock`：作为 `java.util.concurrent.locks` 包下的一个类，它基于 AQS（AbstractQueuedSynchronizer）框架实现。使用时必须显式地调用 `lock()` 方法加锁，并务必在 `finally` 代码块中调用 `unlock()` 方法释放锁，以确保锁能被正确释放。

二、功能特性

`ReentrantLock` 提供了 `synchronized` 所不具备的高级特性，使其在复杂并发场景下更具优势：

+ 锁的公平性：`synchronized` 只支持非公平锁，线程获取锁的顺序是随机的。`ReentrantLock` 则可以通过构造方法选择公平锁（按等待顺序获取）或非公平锁（默认，吞吐量更高）。
+ 响应中断：`ReentrantLock` 的 `lockInterruptibly()` 方法允许等待锁的线程响应中断，从而避免线程无限期地等待下去。`synchronized` 则不支持。
+ 超时尝试：`ReentrantLock` 的 `tryLock(long time, TimeUnit unit)` 方法允许线程在指定时间内尝试获取锁，如果超时则放弃，这为处理死锁或实现降级逻辑提供了可能。`synchronized` 无法做到。
+ 多条件队列：`ReentrantLock` 可以绑定多个 `Condition` 对象，实现精细化的线程等待与唤醒（例如在生产者-消费者模型中，可以分别唤醒“队列不满”和“队列不空”的线程）。而 `synchronized` 只能配合 `wait()/notify()` 使用，每个对象只有一个等待队列，唤醒操作不够精准。

三、核心差异速查

| 对比维度 | `synchronized` | `ReentrantLock` |
| :--- | :--- | :--- |
| 实现层面 | JVM 层面，基于 Monitor | JDK 层面，基于 AQS |
| 锁的释放 | 自动释放，安全便捷 | 必须手动释放，需写在 `finally`<br/> 中 |
| 公平锁 | 不支持，仅为非公平锁 | 支持，可配置公平或非公平 |
| 高级功能 | 不支持中断、超时、多条件 | 支持可中断、超时尝试、多条件队列 |
| 性能表现 | JDK 1.6 后优化显著，低竞争下性能优异 | 在高竞争场景下性能更稳定，控制力更强 |

四、如何选择

+ 首选`synchronized`：在绝大多数简单的同步场景下，`synchronized` 凭借其代码简洁、不易出错的特性，是首选方案。JDK 对其持续的性能优化也使其在低中竞争场景下表现非常出色。
+ 选用`ReentrantLock`：当你需要实现公平锁、可中断锁、超时锁或多条件精准唤醒等高级功能时，`ReentrantLock` 则是更合适的选择。它提供了更细粒度的控制，但代价是代码更复杂，对开发者的要求也更高。

### 19. 介绍一下Redis红锁？

Redis 红锁（RedLock）是由 Redis 作者 Antirez 提出的一种分布式锁算法，旨在解决单节点或主从架构 Redis 在分布式环境下因节点故障导致锁失效、从而破坏互斥性的问题。

一、核心思想：多数派原则

红锁的核心思想是“少数服从多数”。它不依赖于单个 Redis 实例，而是要求客户端向多个（通常为 5 个）完全独立的 Redis 主节点发起加锁请求。只有当客户端在超过半数（即 N/2 + 1 个）的节点上成功加锁，并且整个加锁过程的总耗时小于锁的有效期时，才认为真正获取了分布式锁。这种机制确保了即使部分节点发生故障，锁的安全性依然能得到保障。

二、实现流程

1. 加锁：客户端首先记录当前时间戳，然后并发地向所有 N 个独立的 Redis 节点发送加锁请求（使用 `SET key value NX PX timeout` 命令，其中 value 为唯一标识，如 UUID）。客户端统计成功加锁的节点数量，并计算总耗时。
2. 判断成功：加锁成功需同时满足两个条件：① 成功加锁的节点数 ≥ N/2 + 1；② 加锁总耗时 < 锁的有效期（TTL）。
3. 解锁：无论加锁成功与否，客户端都需要向所有 N 个节点发送解锁请求。解锁时必须使用 Lua 脚本，先校验锁的 value 是否匹配，再执行删除操作，以防止误删其他客户端的锁。

三、争议与局限

红锁自提出以来便伴随着巨大争议，尤其是分布式系统专家 Martin Kleppmann 对其安全性提出了根本性质疑：

+ 时钟依赖：红锁的正确性严重依赖于各个 Redis 节点的本地时钟稳定。如果发生时钟回拨或漂移，可能导致锁提前过期，从而破坏互斥性。
+ GC 停顿：当持有锁的客户端发生长时间的垃圾回收（GC）停顿，停顿时间超过锁的 TTL 时，锁会自动释放。此时其他客户端可以获取锁，导致两个客户端同时进入临界区，红锁无法防护此类问题。

四、适用场景与建议

红锁部署和运维成本较高（需维护多个独立 Redis 实例），且性能低于单实例锁。因此，它仅适用于对锁的一致性要求极高、能接受一定性能损耗、并可严格管控节点时钟稳定性的场景。

在实际开发中，通常不建议手动实现红锁算法。对于 Java 应用，推荐使用成熟的客户端库 Redisson，它封装了 `RedissonRedLock`，并提供了看门狗（Watchdog）等机制来自动续期，简化了使用复杂度。对于要求强一致性的核心场景，更推荐使用 ZooKeeper 或 etcd 等基于共识算法（如 Raft）的协调服务来实现分布式锁。

### 20. Spring为什么要用三级缓存？如果没有三级缓存会出现什么问题？

Spring 引入三级缓存的核心目的，是为了在解决 Bean 之间循环依赖问题的同时，完美兼容 AOP（面向切面编程）动态代理机制。这是一个在“提前暴露引用”和“保证代理正确性”之间取得精妙平衡的设计。

简单来说，一级缓存存放完全初始化好的成品 Bean，二级缓存存放提前暴露的半成品 Bean（已实例化但未完成属性注入和初始化），而三级缓存是整个机制的灵魂，它存放的不是 Bean 本身，而是一个能生成 Bean 早期引用的工厂（`ObjectFactory`）。

一、核心目的：兼容 AOP 动态代理

如果没有 AOP，仅用一级和二级缓存就足以解决循环依赖。问题的关键在于 AOP 代理对象的创建时机。

+ AOP 代理的创建时机：Spring AOP 代理对象是在 Bean 生命周期的 `BeanPostProcessor` 后置处理阶段生成的，这个时间点晚于属性注入。
+ 循环依赖的解决时机：解决循环依赖需要在属性注入阶段就提前暴露一个 Bean 的引用，否则就会陷入 A 依赖 B，B 又依赖 A 的死循环。

这就产生了一个矛盾：在属性注入时，AOP 代理对象还未生成，但循环依赖又急需一个引用来打破僵局。

二、如果没有三级缓存会出现什么问题？

如果只有两级缓存，我们只能提前暴露原始的 Bean 对象（半成品）。这会导致一个严重问题：依赖方注入的是原始对象，而 Spring 容器最终使用的是代理对象，造成对象不一致，从而使 AOP 增强（如`@Transactional`事务）失效。

举个例子：
假设 `ServiceA` 依赖 `ServiceB`，`ServiceB` 也依赖 `ServiceA`，并且 `ServiceA` 标注了 `@Transactional`。

1. Spring 开始创建 `ServiceA`，实例化后将其原始对象放入二级缓存。
2. 在注入 `ServiceB` 时，Spring 去创建 `ServiceB`。
3. `ServiceB` 需要注入 `ServiceA`，于是从二级缓存中拿到了 `ServiceA` 的原始对象并完成注入。
4. `ServiceB` 创建完成，进入一级缓存。
5. `ServiceA` 继续初始化，最终生成了事务代理对象，并放入一级缓存。

最终结果是：`ServiceB` 持有的 `ServiceA` 是没有事务功能的原始对象，而容器中真正管理的 `ServiceA` 是有事务功能的代理对象。这破坏了单例 Bean 的一致性，导致事务注解失效。

三、三级缓存如何巧妙解决？

三级缓存通过引入一个 `ObjectFactory`（一个 Lambda 表达式）来解决这个矛盾，其核心在于延迟执行和智能判断。

1. 延迟暴露：在 `ServiceA` 实例化后，Spring 不会立即创建其早期引用，而是将一个 `ObjectFactory` 放入三级缓存。这个工厂里封装了“如何生成早期引用”的逻辑。
2. 按需创建：当 `ServiceB` 需要注入 `ServiceA` 时，它会去三级缓存找到这个工厂，并调用其 `getObject()` 方法。
3. 智能判断：`getObject()` 方法内部会判断 `ServiceA` 是否需要 AOP 代理。如果需要，它就立即创建并返回 `ServiceA` 的代理对象；如果不需要，则返回原始对象。
4. 升级缓存：这个提前生成的代理对象（或原始对象）会被立即放入二级缓存，同时从三级缓存中移除对应的工厂。

通过这种方式，`ServiceB` 拿到的 `ServiceA` 引用，与 Spring 容器最终生成并放入一级缓存的对象是完全一致的代理对象，从而完美解决了循环依赖和 AOP 代理之间的矛盾。

### 21. 为什么JDK提供非线程安全的HashMap，而非统一鼓励使用ConcurrentHashMap？

JDK 之所以保留非线程安全的 `HashMap`，而不是统一鼓励使用 `ConcurrentHashMap`，核心原因在于“性能与场景的权衡”。在单线程环境下，`HashMap` 凭借其极简的设计提供了极致的性能，而 `ConcurrentHashMap` 为了保证线程安全，不可避免地引入了额外的开销。如果强制所有场景都使用 `ConcurrentHashMap`，会导致不必要的性能损耗。

以下是具体的几个关键原因：

一、性能差异：无锁 vs 有锁

+ HashMap（极致速度）：它是为单线程环境设计的，内部没有任何同步机制（锁或 CAS）。这意味着在进行 `put` 或 `get` 操作时，不需要进行复杂的原子指令或锁竞争检查，因此在单线程场景下，它的读写效率是最高的。
+ ConcurrentHashMap（安全代价）：为了保证多线程下的数据一致性，它使用了 CAS（Compare-And-Swap） 和 synchronized（JDK 1.8）或分段锁（JDK 1.7）。即使是读操作，虽然通常是无锁的，但也需要依赖 `volatile` 变量来保证可见性。这些机制虽然保证了安全，但相比于 `HashMap` 的“裸奔”，确实存在指令层面的性能损耗。在不需要线程安全的场景下（如局部变量、单线程任务），使用它会是一种资源浪费。

二、功能特性：Null 值的语义

+ HashMap：允许键和值为 `null`。这在很多业务场景中非常有用，比如用 `null` 值表示“键存在但无值”的状态。
+ ConcurrentHashMap：严禁键或值为 `null`。这是为了避免并发环境下的歧义：当 `get(key)` 返回 `null` 时，你无法判断是“键不存在”还是“值本身就是 `null`”。在单线程中可以通过 `containsKey` 二次确认，但在多线程下，两次调用之间数据可能已经变化，导致判断失效。如果统一使用 `ConcurrentHashMap`，开发者将无法存储 `null` 值，限制了功能的灵活性。

三、内存与开销

+ HashMap：结构相对简单，仅维护数组、链表和红黑树节点。
+ ConcurrentHashMap：除了存储数据外，还需要维护额外的同步控制结构（如 `sizeCtl` 等 volatile 变量、锁对象等）。对于海量小对象的存储，这些额外的元数据会占用更多的内存空间。

四、总结：何时选择哪一个？

| 维度 | HashMap | ConcurrentHashMap |
| :--- | :--- | :--- |
| 核心定位 | 单线程 / 线程封闭场景 | 多线程并发共享场景 |
| 线程安全 | ❌ 不安全（并发下可能死循环或数据丢失） | ✅ 安全（CAS + synchronized） |
| Null 支持 | ✅ 允许 | ❌ 禁止（抛出异常） |
| 性能 | ⚡ 单线程下最快 | 🐢 略慢（有同步开销），但并发能力强 |
| 适用场景 | 方法内部变量、单线程处理、无需共享的数据 | 全局缓存、共享配置、多线程任务交互 |

一句话概括： JDK 提供 `HashMap` 是为了让开发者在确定没有并发风险的场景下，能够享受到最高性能和完整功能（如 null 值）；而 `ConcurrentHashMap` 则是为了解决多线程共享数据时的安全问题。两者各司其职，互为补充。

### 22. 介绍一下SpringBoot的自动装配原理？

Spring Boot 的自动装配（Auto-Configuration）是其“约定优于配置”理念的核心实现。它能够在应用启动时，根据项目的类路径依赖、已存在的 Bean 以及配置文件等信息，自动推断并注册所需的组件，从而极大地简化了开发者的配置工作。

其核心原理可以概括为以下三个关键步骤：

一、启动入口：`@EnableAutoConfiguration`

自动装配的起点是启动类上的 `@SpringBootApplication` 注解。这是一个复合注解，其中包含的 `@EnableAutoConfiguration` 是开启自动配置的关键。该注解通过 `@Import` 导入了一个名为 `AutoConfigurationImportSelector` 的选择器，它的作用就是负责加载所有候选的自动配置类。

二、加载配置：SPI 机制

`AutoConfigurationImportSelector` 会利用 Java 的 SPI（Service Provider Interface）机制，扫描类路径下的特定文件来获取所有自动配置类的全限定名。

+ 在 Spring Boot 2.7 及之前版本，它读取的是 `META-INF/spring.factories` 文件。
+ 在 Spring Boot 3.x 版本，则改为读取 `META-INF/spring/org.springframework.boot.autoconfigure.AutoConfiguration.imports` 文件。
这些文件中定义了 Spring Boot 提供的所有标准自动配置类，例如 `WebMvcAutoConfiguration`、`DataSourceAutoConfiguration` 等。

三、按需装配：条件注解筛选

加载所有候选配置类后，并不会全部生效。Spring Boot 会通过一系列 `@Conditional` 系列的条件注解进行筛选，确保只有满足特定条件的配置才会被真正应用。这是自动装配“智能化”的灵魂所在。常见的条件注解包括：

+ `@ConditionalOnClass`: 当类路径下存在指定的类时，配置才生效。例如，只有在引入了 `spring-boot-starter-data-redis`，类路径中存在 `RedisTemplate.class` 时，Redis 的自动配置才会生效。
+ `@ConditionalOnMissingBean`: 当 Spring 容器中不存在指定的 Bean 时，配置才生效。这保证了开发者自定义的 Bean 可以覆盖 Spring Boot 的默认配置。
+ `@ConditionalOnProperty`: 当配置文件（如 `application.yml`）中存在指定的属性时，配置才生效。

通过“启动入口 → 加载配置 → 条件筛选”这一流程，Spring Boot 实现了根据项目实际情况进行按需、智能的自动装配。

### 23. 怎么判断SQL有没有走索引？

判断 SQL 是否走了索引，最权威且常用的方法是使用 `EXPLAIN`命令查看执行计划。通过分析 `EXPLAIN` 的输出结果，重点关注 `type`、`key`、`rows` 和 `Extra` 这四个字段，即可准确判断索引的使用情况。

一、核心判断指标

在 `EXPLAIN` 的结果中，你可以通过以下四个维度快速定位问题：

1. `key`（实际使用的索引）

+ 这是最直接的判断依据。如果该字段显示为 `NULL`，说明没有使用任何索引，进行了全表扫描。
+ 如果显示了具体的索引名称（如 `idx_user_id` 或 `PRIMARY`），则说明命中了该索引。

1. `type`（连接类型/访问类型）

+ 这代表了 MySQL 查找数据的方式，性能从好到坏依次为：`system` > `const` > `eq_ref` > `ref` > `range` > `index` > `ALL`。
+ 重点关注：如果 `type` 为 `ALL`，代表进行了全表扫描，这是性能优化的重点对象，意味着索引失效或未建立。
+ 理想情况：至少达到 `range`（范围扫描）或 `ref`（非唯一索引扫描）级别，最好能达到 `const`（主键或唯一索引查询）。

1. `Extra`（额外信息）

+ `Using index`：极好。表示使用了覆盖索引，查询的数据直接在索引树中就能获取，无需回表查询数据行，效率最高。
+ `Using filesort`：坏。表示 MySQL 无法利用索引完成排序，需要进行额外的文件排序操作，性能较差。
+ `Using temporary`：非常坏。表示使用了临时表（通常在 `GROUP BY` 或 `ORDER BY` 时出现），应尽量避免。

1. `rows`（扫描行数）

+ 这是 MySQL 估算的需要扫描的行数。数值越小越好。如果 `rows` 接近表的总行数，说明索引的筛选能力很弱或失效。

二、常见索引失效场景

即使你建立了索引，`EXPLAIN` 也可能显示 `key: NULL` 或 `type: ALL`。以下是导致索引失效的常见原因：

| 失效原因 | 示例 SQL | 解决方案 |
| :--- | :--- | :--- |
| 最左前缀原则 | 联合索引`(a,b,c)`<br/>，查询只用`WHERE b=1` | 遵循最左前缀，或使用`a`<br/>列查询 |
| 隐式类型转换 | 字符串字段 `phone`<br/> 查询写成 `WHERE phone=123`<br/> (无引号) | 确保查询值类型与字段类型一致（加引号） |
| 对索引列运算 | `WHERE YEAR(create_time) = 2023` | 改为范围查询：`WHERE create_time BETWEEN ...` |
| 模糊查询 | `WHERE name LIKE '%abc'`<br/> (以通配符开头) | 尽量使用 `LIKE 'abc%'`<br/>，或使用全文索引 |
| OR 条件 | `WHERE id=1 OR name='abc'`<br/> (非索引列参与 OR) | 确保 OR 两边都有索引，或改写为 `UNION` |

三、进阶：验证真实使用情况

`EXPLAIN` 只能告诉你 SQL 理论上会怎么走，而在生产环境中，你还需要知道索引实际上有没有被用到。

+ 查看运行时统计：在 MySQL 5.7+ 中，可以查询 `performance_schema.table_io_waits_summary_by_index_usage` 表。如果某个索引的 `COUNT_FETCH` 长期为 0，说明它是“僵尸索引”，不仅浪费空间还拖慢写入速度，建议删除。
+ 慢查询日志：开启慢查询日志并设置 `log_queries_not_using_indexes = ON`，可以帮你抓出那些实际运行中未走索引的 SQL 语句。

### 24. Spring存放Bean实例的IOC容器底层用的是什么数据结构？

Spring IoC 容器（以默认的 `DefaultListableBeanFactory`及其父类为例）底层主要使用 `ConcurrentHashMap`或其类似的`Map`实现 来存储和管理 Bean 的定义与实例。

具体来说，其核心结构包括：

+ Bean 定义注册表：通常是一个 `Map<String, BeanDefinition>`，用于存储所有 Bean 的定义信息（如 `RootBeanDefinition`），键是 Bean 的名称。这为后续的实例化、依赖注入提供了“蓝图”。
+ 单例 Bean 缓存池：这是最核心的容器，通常是一个 `ConcurrentHashMap`或经过同步包装的 `Map`（如 `DefaultSingletonBeanRegistry`中的 `singletonObjects`），用于缓存所有已创建完成的单例 Bean 实例，键是 Bean 的名称，值是实例化好的 Bean 对象。使用 `ConcurrentHashMap`主要是为了在保证线程安全的前提下，实现高效的并发读取（因为 Spring 容器启动后，读操作远多于写操作）。

为什么是 Map 结构？

因为 IoC 容器最核心、最频繁的操作就是 通过 Bean 的名称（或类型）快速查找并获取对应的 Bean 实例，这正符合 Map 数据结构 O(1) 时间复杂度查找 的特性，能提供极高的访问性能。此外，三级缓存解决循环依赖时，其每一级缓存本身也都是一个 Map 结构。

一句话总结：Spring IoC 容器底层核心是一个以 Bean 名称为键、Bean 实例（或定义）为值的 Map（通常是 `ConcurrentHashMap`），以此实现高效、线程安全的 Bean 存储、管理和查找。

### 25. @Autowired和@Resource注解的区别是什么？

`@Autowired`默认按类型注入，是 Spring 的首选方式；`@Resource`默认按名称注入，是 Java 标准注解。

在 Spring 项目中，通常优先使用 `@Autowired`，当需要按名称注入或避免与 Spring 强绑定时，可选用 `@Resource`。

### 26. Redis持久化有哪些？对比一下

Redis持久化主要有RDB和AOF两种方式。

RDB是定时全量快照，恢复速度快且文件紧凑，但可能丢失最后一次快照后的数据，适合容灾备份。

Spring是一个开源的Java全栈式轻量级开发框架，其核心是IoC（控制反转）容器和AOP（面向切面编程）。

IoC容器通过依赖注入管理对象生命周期与依赖关系，实现了组件间的解耦，让程序更易于测试与维护。Spring生态极其丰富，例如Spring MVC用于Web开发，Spring Data简化数据访问，而Spring Boot通过自动配置和约定优于配置的理念，极大地简化了基于Spring的独立应用创建，让我们能快速构建可运行的、生产级的微服务。

### 28. 讲一讲Redis中的热Key？可能会有什么问题？

在Redis中，热Key指的是某个特定的Key在短时间内被极高频率地访问（如热门商品、爆款话题）。

这会导致两个主要问题：首先，数据倾斜，大量请求集中落到Redis集群的某一个节点上，使其CPU、网络和带宽压力激增，可能拖垮该实例，影响整个集群的稳定性；其次，容易击穿本地缓存，如果业务层有本地缓存，对该Key的并发更新可能使其在本地频繁失效，导致所有请求穿透到Redis，进一步放大压力。

在Java后端开发中，常见的应对思路包括使用本地缓存（如Caffeine）做多级缓存、对热Key进行拆分（如添加随机后缀分散存储），或通过服务端读写分离来分散读压力。

### 29. 讲一下Spring AOP的大概流程和机制？

Spring AOP（面向切面编程）的核心机制是动态代理。它允许开发者在不修改原有业务代码的前提下，将日志记录、事务管理、权限校验等通用功能（称为“横切关注点”）模块化，并在运行时动态地“织入”到指定的业务方法中，从而实现业务逻辑与系统级功能的解耦。

一、核心机制：动态代理

Spring AOP 的本质是在运行时为目标对象（被增强的 Bean）创建一个代理对象，由这个代理对象来控制对原始方法的调用，并在调用前后插入预定义的增强逻辑。它会根据目标类的特点自动选择代理方式：

1. JDK 动态代理：如果目标对象实现了至少一个接口，Spring 会优先使用 JDK 原生的 `java.lang.reflect.Proxy` 来创建代理。这种方式生成的代理类会实现目标对象的所有接口。
2. CGLIB 代理：如果目标对象没有实现任何接口，Spring 则会使用 CGLIB 库。它通过 ASM 字节码操作框架，在运行时动态生成一个目标类的子类作为代理对象，并重写其非 `final` 方法来植入增强逻辑。

二、执行流程：从配置到运行

Spring AOP 的工作流程可以清晰地分为三个阶段：

1. 配置解析阶段（启动时）
Spring 容器启动时，会扫描并解析所有被 `@Aspect` 注解标记的切面类。它会识别其中的切点（`@Pointcut`，定义“在哪里”增强）和通知（`@Before`, `@After` 等，定义“做什么”增强），并将它们组合成 `Advisor`（通知器）对象，注册到容器中。
2. 代理创建阶段（Bean 初始化时）
在 Spring 容器初始化每个 Bean 之后，一个名为 `BeanPostProcessor` 的后置处理器会介入。它会检查当前 Bean 是否匹配任何已注册的切点。如果匹配，Spring 就会根据上述的动态代理规则，为该 Bean 创建一个代理对象，并用这个代理对象替换掉原始的 Bean 实例，注入到其他依赖它的组件中。
3. 方法调用与织入阶段（运行时）
当客户端代码调用 Bean 的方法时，实际调用的是代理对象的方法。代理对象会拦截这次调用，根据方法签名查找所有匹配的 `Advisor`，并按顺序执行一个由通知逻辑组成的拦截器链（责任链模式）。这个链条会依次执行前置通知、目标方法、后置通知、返回通知或异常通知，最终将结果返回给调用者。

三、关键概念与注意事项

+ 通知（Advice）：定义了增强的具体逻辑和时机。Spring AOP 支持五种类型：`@Before`（前置）、`@After`（后置）、`@AfterReturning`（返回后）、`@AfterThrowing`（异常后）和 `@Around`（环绕）。其中，`@Around` 通知功能最强大，可以控制目标方法是否执行以及何时执行。
+ 局限性：Spring AOP 仅作用于由 Spring 容器管理的 Bean。对于通过 `new` 关键字直接创建的对象，或者类内部方法之间的自调用，AOP 增强都不会生效，因为它们绕过了代理对象。

### 30. JDK8和JDK17各自使用的默认垃圾回收器是什么？

在 JDK 8 中，默认的垃圾回收器是 Parallel Scavenge（用于新生代） 和 Parallel Old（用于老年代） 的组合，即Parallel GC。这套组合以最大化吞吐量为主要设计目标。

而从 JDK 9 开始，G1 就成为了默认回收器，因此 JDK 17 的默认垃圾回收器是 G1（Garbage-First）。G1 的设计目标是可控的低停顿时间，它通过将堆划分为多个区域（Region）并进行预测性的垃圾回收，来更好地平衡吞吐量和延迟。

### 31. 实例加锁和类加锁的区别是什么？

实例加锁和类加锁是Java中`synchronized`关键字在不同作用域上的应用，核心区别在于锁定的对象（锁监视器）不同。

实例加锁锁定的是当前对象实例（`this`）。当一个线程访问某个对象的`synchronized`实例方法或代码块时，锁住的是这个对象本身，其他线程依然可以同时访问该类的其他对象实例的同步方法，因为锁不同。

类加锁锁定的是整个类的Class对象（`ClassName.class`）。当一个线程访问某个类的`synchronized`静态方法或代码块时，锁住的是这个类，这会阻止其他线程同时访问该类的任何实例的所有同步静态方法，因为所有实例共享同一把类锁。

简单来说，实例锁保护的是单个对象实例的非静态数据，而类锁保护的是属于整个类的静态数据。如果错误地用实例锁去保护静态共享资源，就会导致线程安全问题。

### 32. 讲一讲JVM的常见调优经验？

JVM 调优是一项系统性工作，其核心目标并非盲目追求极限性能，而是解决实际问题，例如频繁的垃圾回收（GC）、过长的GC停顿时间（Stop-The-World）或内存溢出（OOM）。调优前，明确业务是追求高吞吐量还是低延迟，是制定正确策略的前提。

一、调优前的关键一步：监控与诊断

在动手调整任何参数之前，必须先通过监控和诊断工具定位问题根源。盲目调优往往适得其反。

+ GC日志分析：开启GC日志是生产环境排查问题的基础，它能直观反映GC的频率、类型和耗时。
+ 实时监控：使用 Prometheus + Grafana 等监控平台，可以持续观察堆内存使用率、GC暂停时间、线程数等关键指标，并设置告警。
+ 诊断工具：当出现问题时，可以利用 `jstat` 查看GC统计信息，用 `jmap` 导出堆快照，用 `jstack` 分析线程状态。阿里开源的 Arthas 更是线上不停机排查的利器，可以实时查看方法耗时、内存占用等情况。

二、核心调优策略：从宏观到微观

调优通常遵循一个清晰的步骤，从整体架构选择到具体参数微调。

1. 选择合适的垃圾回收器 (Garbage Collector)
这是影响性能最关键的决策。不同的回收器适用于不同的场景：

+ G1 GC：当前大多数应用的首选，它在吞吐量和延迟之间取得了很好的平衡，尤其适合大内存应用。
+ Parallel GC：注重高吞吐量，适合后台批处理任务。
+ ZGC / Shenandoah：追求极致的低延迟（亚毫秒级停顿），适用于对响应时间要求苛刻的实时系统。

1. 优化内存配置
合理的内存划分是减少GC频率的基础。

+ 固定堆大小：将初始堆大小（`-Xms`）和最大堆大小（`-Xmx`）设置为相同值，可以避免JVM在运行时动态调整堆大小带来的性能开销和不稳定。
+ 调整内存区域：根据对象的生命周期特点，合理设置新生代与老年代的比例（`-XX:NewRatio`），或调整元空间大小（`-XX:MetaspaceSize`）以避免频繁扩容。

1. 微调GC参数
在选定回收器后，可以根据目标进行精细化调整。例如，对于G1回收器，可以设置期望的最大GC停顿时间目标（`-XX:MaxGCPauseMillis`），JVM会尽力在此目标内完成回收。

三、重要的实战经验与原则

+ 代码优化优先：JVM调优是“锦上添花”，而非“雪中送炭”。解决内存泄漏（如未关闭的资源、静态集合滥用）、减少临时对象创建、使用高效的集合和缓存库（如Caffeine），这些代码层面的优化往往比调整JVM参数效果更显著。
+ 灰度发布与基准测试：任何生产环境的参数变更都必须经过充分的基准测试，并通过灰度发布逐步验证效果，切忌直接全量上线。
+ 容器化环境感知：在Docker或K8s等容器环境中，务必确保JVM能正确识别容器的资源限制，例如启用 `-XX:+UseContainerSupport` 参数。

### 33. order by、group by会不会导致索引失效？

`ORDER BY` 和 `GROUP BY` 本身不会直接导致索引失效，但它们能否有效利用索引，取决于字段顺序、查询条件以及索引结构是否匹配。如果设计不当，不仅无法利用索引加速，反而会触发额外的排序或临时表操作，严重拖慢查询性能。

一、核心原则：利用索引的有序性

MySQL 中 B+ 树索引本身就是有序的。`ORDER BY` 和 `GROUP BY` 优化的核心目标，就是让数据库能够直接利用索引中已有的顺序，从而避免昂贵的额外操作：

+ 避免`Using filesort`：当 `ORDER BY` 无法利用索引排序时，MySQL 必须在内存或磁盘中进行额外的排序，这在数据量大时非常消耗资源。
+ 避免`Using temporary`：当 `GROUP BY` 无法利用索引分组时，MySQL 通常需要创建一个临时表来存放分组结果，同样会带来性能损耗。

二、导致索引失效或效率低下的常见场景

即使你在 `ORDER BY` 或 `GROUP BY` 的字段上建立了索引，以下情况也会导致索引无法被有效利用：

1. 违反最左前缀原则
对于联合索引 `(a, b, c)`，`ORDER BY` 或 `GROUP BY` 必须从最左边的字段 `a` 开始，并且字段顺序要连续。

+ 失效示例：`ORDER BY b` 或 `ORDER BY a, c`（跳过了 `b`）。索引只能用于 `a` 的排序，`c` 仍需额外排序。

1. 排序或分组方向不一致
索引的排序方向（ASC/DESC）需要与查询语句保持一致。

+ 失效示例：索引为 `(a ASC, b ASC)`，但查询为 `ORDER BY a ASC, b DESC`。MySQL 无法利用索引中 `b` 的逆序，会触发 `Using filesort`。（注：MySQL 8.0 开始支持降序索引，可以解决此问题）

1. WHERE 条件中包含范围查询
这是一个非常隐蔽的陷阱。在联合索引 `(a, b)` 中，如果 `WHERE` 条件对 `a` 使用了范围查询（如 `>`, `<`, `BETWEEN`），那么索引中 `b` 列的顺序性就被破坏了，无法再用于 `ORDER BY` 或 `GROUP BY`。

+ 失效示例：`WHERE a > 100 ORDER BY b`。虽然 `b` 是索引的一部分，但由于 `a` 是范围查询，`b` 在 `a > 100` 的结果集中是无序的。

1. 对索引列进行运算或使用函数
任何对索引列的“加工”都会导致索引失效。

+ 失效示例：`GROUP BY YEAR(create_time)` 或 `ORDER BY UPPER(user_name)`。数据库无法使用 `create_time` 或 `user_name` 的原始索引。

1. 字符集不匹配导致隐式转换
在多表 `JOIN` 时，如果关联字段的字符集不一致（例如一个 `utf8`，一个 `utf8mb4`），MySQL 会进行隐式类型转换，这等同于对索引列使用了函数，导致索引失效。

三、总结与优化建议

| 场景 | 关键点 | 优化建议 |
| :--- | :--- | :--- |
| ORDER BY | 避免`Using filesort` | 确保排序字段与联合索引的字段顺序和排序方向完全一致。 |
| GROUP BY | 避免 `Using temporary` | 尽量让分组字段成为联合索引的最左前缀。 |
| WHERE + ORDER/GROUP BY | 范围查询会中断索引 | 优先将等值查询的字段放在联合索引的前面，范围查询字段放后面。 |
| 通用规则 | 保持索引纯净 | 避免在 `ORDER BY`<br/> / `GROUP BY`<br/> 中对字段使用函数、表达式或类型转换。 |

总而言之，`ORDER BY` 和 `GROUP BY` 的索引优化是一个系统工程，需要结合 `WHERE` 条件、索引设计和 SQL 写法综合考量。通过 `EXPLAIN` 命令检查执行计划中的 `Extra` 字段，是判断是否存在性能问题的最直接方法。

### 34. RabbitMQ和Kafka有什么区别？

RabbitMQ 和 Kafka 虽然都是消息中间件，但它们的设计初衷和核心定位截然不同。简单来说，RabbitMQ 是一个“智能的消息代理”，侧重于复杂的路由和可靠投递；而 Kafka 是一个“分布式的日志流平台”，侧重于海量数据的高吞吐处理。

以下是它们在架构、性能和使用场景上的关键区别：

一、架构模型：智能代理 vs 智能消费者

+ RabbitMQ（推模式）：采用“智能代理/简单消费者”模式。消息由 Broker 负责路由、排队和推送。Broker 会追踪消息的状态（是否被消费、是否确认）。一旦消费者确认（ACK），消息通常就会被删除。它像一个邮局，负责把信件精准地送到收件人手中。
+ Kafka（拉模式）：采用“简单代理/智能消费者”模式。Broker 不负责追踪消息状态，只是将消息追加写入磁盘（类似日志文件）。消费者通过 Offset（偏移量） 自己记录读到了哪里，并主动去拉取消息。消息会被保留一段时间（可配置），支持重复消费和回溯。它像一个传送带，数据一直在流转，谁需要谁去拿。

二、性能与吞吐量：低延迟 vs 高吞吐

+ RabbitMQ：追求低延迟（亚毫秒级）。它的吞吐量通常在万级/秒，虽然也很高，但在海量数据堆积时性能会下降。它更适合处理复杂的业务逻辑，对单条消息的响应速度要求极高。
+ Kafka：追求高吞吐（百万级/秒）。它利用顺序写磁盘、零拷贝和批量发送等技术，能够轻松处理 TB 级的数据流。虽然延迟也是毫秒级，但相比 RabbitMQ 略高，不过在面对海量日志或大数据场景时，其吞吐量优势巨大。

三、路由与功能：灵活路由 vs 简单分区

+ RabbitMQ：拥有极强的路由能力。通过 Exchange（交换机）、Binding（绑定）和 Routing Key，可以实现直连、广播、主题匹配等多种复杂的路由策略。此外，它还原生支持死信队列、延迟队列、优先级队列等丰富的业务特性。
+ Kafka：路由逻辑相对简单，主要基于 Topic 和 Partition（分区）。消息通过 Key 哈希分配到特定分区，保证分区内的有序性。它缺乏 RabbitMQ 那样灵活的路由机制，也不原生支持死信队列（通常需要通过外部 Topic 实现）。

四、核心差异速查

| 对比维度 | RabbitMQ | Kafka |
| :--- | :--- | :--- |
| 核心定位 | 消息代理，侧重业务解耦与可靠投递 | 分布式日志流，侧重大数据管道与流处理 |
| 消费模型 | 推模式，消息消费后通常删除 | 拉模式，基于 Offset 消费，支持回放 |
| 吞吐量 | 万级/秒（低延迟） | 百万级/秒（高吞吐） |
| 路由能力 | 极强（支持复杂路由规则） | 较弱（基于 Partition 分区） |
| 消息保留 | 消费即删（或 TTL 过期） | 按时间或大小保留（可回溯历史数据） |
| 可靠性 | 强（支持事务、ACK 机制） | 强（副本机制，但侧重最终一致性） |

五、选型建议：该用哪一个？

+ 选择 RabbitMQ：

+ 如果你的场景是复杂的业务系统，如订单处理、支付交易、任务分发。
+ 你需要复杂的路由规则（例如：根据消息内容路由到不同队列）。
+ 你需要延迟队列、死信处理或严格的可靠性保证（如金融级事务）。
+ 系统对实时性（低延迟）要求极高。

+ 选择 Kafka：

+ 如果你的场景是日志采集、用户行为追踪、大数据实时计算。
+ 你需要处理海量数据流，对吞吐量要求极高。
+ 你需要消息回溯功能（例如：重新消费昨天的日志来修复数据）。
+ 你需要作为流处理平台（如配合 Flink/Spark Streaming）使用。

一句话总结：如果是为了解耦微服务、处理复杂业务逻辑，选 RabbitMQ；如果是为了构建数据管道、处理海量日志或实时流计算，选 Kafka。

### 35. 现在有2000w条数据，计算一下存储到MySQL中(索引数据结构为B+树)，B+树的层数大概是多少？给出具体的计算过程

在MySQL InnoDB存储引擎中，B+树的层数计算主要取决于几个关键参数：页大小（默认16KB）、主键大小、数据行大小和记录数量。

以常见的配置估算：假设主键为8字节的BIGINT，加上6字节的指针，每个非叶子节点索引条目约14字节。16KB页大约可存储 16 * 1024/14 ≈ 1170 个索引条目。叶子节点存储实际数据，假设每条记录1KB，则每页存储约16条记录。

计算过程：

+ 叶子节点数：2000w/16 ≈ 125w页
+ 第一层非叶子节点：125w/1170 ≈ 1068页
+ 第二层非叶子节点：1068/1170 ≈ 1页（根节点）

因此B+树高度约为3层。实际层数会因数据行大小、索引设计、填充因子等有所浮动，但在此数据量下通常为3-4层，保证了良好的查询性能。

### 36. 介绍一下MySQL和Redis各自的优势。什么场景下用MySQL更好，什么场景下用Redis更好？

MySQL 和 Redis 是现代应用架构中最常用的两种数据存储系统，它们定位不同，优势互补，常常结合使用。简单来说，MySQL 是用于持久化存储核心业务数据的关系型数据库，而 Redis 是用于高速读写的内存键值存储，常作为缓存或处理特定数据结构。

一、核心优势对比

+ MySQL 的优势

 1. 数据持久化与可靠性：数据默认存储在磁盘上，支持 ACID（原子性、一致性、隔离性、持久性）事务，能保证数据在系统故障后不丢失，是存储核心业务数据的基石。
 2. 复杂查询能力：作为关系型数据库，它使用标准的 SQL 语言，支持多表关联（JOIN）、复杂条件筛选、聚合函数等，能够灵活处理各种复杂的数据查询和分析需求。
 3. 结构化数据管理：基于表结构存储数据，通过外键等机制可以清晰地定义和维护数据之间的关系，非常适合管理用户、订单、商品等结构化信息。

+ Redis 的优势

 1. 极致性能：数据主要存储在内存中，读写速度极快，QPS（每秒查询率）可达十万级以上，能有效应对高并发场景。
 2. 丰富的数据结构：不仅支持简单的键值对，还提供了字符串、哈希（Hash）、列表（List）、集合（Set）、有序集合（Sorted Set）等多种数据结构，可以优雅地解决排行榜、计数器、消息队列等特定编程问题。
 3. 功能多样：除了作为缓存，其原子性操作、发布/订阅、Lua 脚本等特性，使其非常适合实现分布式锁、限流、实时分析等功能。

二、场景选择：何时用谁？

| 场景类型 | 推荐使用 | 典型应用案例 |
| :--- | :--- | :--- |
| 核心业务存储 | MySQL | 用户账号信息、订单交易记录、商品库存、支付流水等需要强一致性和事务保证的数据。 |
| 复杂关联查询 | MySQL | 生成月度财务报表、查询用户近一年的所有订单、多条件组合筛选商品等。 |
| 热点数据缓存 | Redis | 将商品信息、用户资料等高频访问的数据缓存在 Redis 中，减轻 MySQL 的查询压力，提升响应速度。 |
| 实时计数与排行 | Redis | 文章阅读量、视频点赞数、用户积分排行榜、秒杀活动库存扣减等。 |
| 会话（Session）管理 | Redis | 在分布式系统中，将用户登录状态（Session）存储在 Redis 中，实现多服务实例间的会话共享。 |
| 分布式锁 | Redis | 在分布式环境下，利用 `SETNX`<br/> 等命令实现互斥锁，保证同一时间只有一个服务实例能操作共享资源。 |

三、最佳实践：协同工作

在实际开发中，MySQL 和 Redis 并非二选一的关系，而是协同工作、优势互补的黄金搭档。

最常见的模式是 “MySQL + Redis 缓存” 架构：

+ MySQL 作为“单一事实来源”，负责持久化存储所有核心业务数据，保证数据的准确性和可靠性。
+ Redis 作为高速缓存层，存放从 MySQL 中读取的热点数据。当应用需要查询数据时，先查 Redis，如果命中则直接返回；如果未命中，再查询 MySQL，并将结果写入 Redis，同时设置一个合理的过期时间。

这种架构完美结合了 MySQL 的数据可靠性和 Redis 的极致性能，既能保证数据安全，又能大幅提升系统在高并发场景下的响应速度和吞吐量。

### 37. 介绍一下在分布式系统中实现分布式锁的实现方案

在分布式系统中，实现分布式锁主要有三种主流方案，它们在性能、一致性和实现复杂度上各有侧重。

一、基于数据库的实现

这是最基础的方案，主要利用数据库的固有特性来实现锁。

+ 核心原理：通过创建一张锁表，利用字段的唯一索引来保证互斥性；或者使用 `SELECT ... FOR UPDATE` 的悲观锁机制来锁定特定行。
+ 优点：实现简单，无需引入额外的中间件。
+ 缺点：性能较差，因为数据库的I/O开销大，难以应对高并发场景。同时，它存在单点故障风险，并且锁通常没有自动过期机制，需要手动处理以防死锁。

二、基于 Redis 的实现

这是目前互联网高并发场景下最流行的方案，利用 Redis 的内存操作实现高性能锁。

+ 核心原理：使用 `SET key value NX PX milliseconds` 这样的原子命令来加锁，确保互斥性和自动过期。解锁时，通常通过 Lua 脚本来校验锁的持有者身份再删除，防止误删。成熟的客户端如 Redisson 还提供了“看门狗”机制来自动续期，解决了业务执行时间超过锁超时时间的问题。
+ 优点：性能极高，响应快，并且生态成熟，功能丰富。
+ 缺点：Redis 遵循 AP 模型，在主从切换的极端情况下，可能会出现锁丢失的风险，属于弱一致性。

三、基于 ZooKeeper 的实现

此方案追求强一致性，常用于金融、支付等对数据准确性要求极高的场景。

+ 核心原理：客户端在 ZooKeeper 上创建一个临时顺序节点。只有序号最小的节点能获得锁，其他节点则监听前一个节点，等待其释放锁（节点被删除）后被唤醒，从而实现公平的分布式锁。
+ 优点：基于 ZAB 协议，提供强一致性（CP 模型），并且临时节点特性可以天然防止死锁。
+ 缺点：由于需要频繁地创建和删除节点，其性能低于 Redis，且实现相对复杂。

### 38. Redis有哪些集群部署的方案？

Redis 的集群部署方案主要可以分为三大类，它们的能力和复杂度逐级递增，适用于不同的业务场景。

一、主从复制 (Master-Slave Replication)

这是最基础的部署模式。它通过设置一个主节点（Master）负责处理写操作，并配置一个或多个从节点（Slave）来异步复制主节点的数据，主要负责处理读操作。

+ 优点：实现了数据的备份和读写分离，可以有效提升读性能。
+ 缺点：不具备自动故障转移能力。当主节点发生故障时，需要人工介入来将从节点提升为主节点，这会导致服务中断。

二、哨兵模式 (Sentinel)

哨兵模式是在主从复制的基础上，引入了哨兵（Sentinel）进程来实现高可用。哨兵集群负责监控主从节点的状态，当主节点不可用时，会自动选举出一个新的主节点，并通知客户端新的主节点地址。

+ 优点：实现了自动化的故障转移，大大提升了服务的可用性。
+ 缺点：虽然解决了高可用问题，但数据仍然全部存储在主节点上，因此无法通过增加节点来水平扩展存储容量和写性能。

三、Redis Cluster 集群

这是 Redis 官方提供的分布式解决方案，旨在实现海量数据存储和高并发访问。它将数据通过哈希槽（Hash Slot）的方式自动分片到多个主节点上，每个主节点可以配备从节点以实现高可用。

+ 优点：同时具备高可用和水平扩展能力。当数据量或访问量增长时，可以通过增加节点来线性扩展集群的存储和处理能力。
+ 缺点：架构和运维相对复杂。例如，不支持跨多个键（Key）的事务等复杂操作。

### 39. 简述一下Spring Bean从创建、依赖注入、初始化、使用到销毁的过程

Spring Bean 的生命周期是一个由容器全程管理的标准化过程，从创建到销毁，每个阶段都提供了丰富的扩展点。整个过程可以概括为以下五个关键阶段：

1. 实例化 (Instantiation)

这是生命周期的起点。Spring 容器根据 Bean 的定义（如 `@Component` 或 `<bean>` 标签），通过反射调用其构造方法，在内存中创建一个原始的 Bean 对象实例。此时，这个对象就像一个“空壳”，其属性尚未被赋值，依赖也未被注入。

1. 属性赋值 / 依赖注入 (Populate Properties / Dependency Injection)

实例化完成后，Spring 会进入属性赋值阶段。容器会解析 Bean 中定义的依赖关系（通过 `@Autowired`、`@Resource` 或 XML 配置），并递归地查找或创建这些依赖 Bean，然后通过反射将它们注入到当前 Bean 的相应属性中。这一步完成了对象之间依赖关系的绑定。

1. 初始化 (Initialization)

这是生命周期中最复杂、扩展点最多的阶段，旨在让 Bean 完全准备好投入使用。此阶段会按顺序执行一系列操作：

1. Aware 接口回调：如果 Bean 实现了 `BeanNameAware`、`BeanFactoryAware` 等接口，Spring 会调用相应方法，将 Bean 的名称、容器实例等信息注入给它，使其能够“感知”到 Spring 容器。
2. `BeanPostProcessor`前置处理：调用所有已注册的 `BeanPostProcessor` 的 `postProcessBeforeInitialization` 方法。这是一个关键的扩展点，允许在初始化前对 Bean 进行修改或增强。
3. 执行自定义初始化方法：按顺序执行多种形式的初始化逻辑，包括 `@PostConstruct` 注解的方法、`InitializingBean` 接口的 `afterPropertiesSet()` 方法，以及在配置中指定的 `init-method`。
4. `BeanPostProcessor`后置处理：调用所有 `BeanPostProcessor` 的 `postProcessAfterInitialization` 方法。Spring AOP 的动态代理就是在这个阶段生成的，原始的 Bean 可能会被一个代理对象所替换。

5. 使用 (In Use)

经过完整的初始化流程后，Bean 已经完全就绪，并被放置在 Spring 容器的单例池中（对于单例 Bean）。此时，应用程序的其他部分可以通过依赖注入或直接调用（如 `getBean()`）来使用这个 Bean，执行其业务逻辑。

1. 销毁 (Destruction)

当 Spring 容器关闭时（例如应用停止），它会负责清理和销毁所有单例 Bean。销毁过程同样遵循特定顺序：首先调用 `@PreDestroy` 注解的方法，然后是 `DisposableBean` 接口的 `destroy()` 方法，最后是配置中指定的 `destroy-method`。这一步主要用于释放数据库连接、关闭文件流等资源，防止内存泄漏。

### 40. 介绍一下Spring中的事务传播机制？

Spring 的事务传播机制（Transaction Propagation）主要解决的是“当一个事务方法被另一个事务方法调用时，这个被调用的方法应该如何参与事务”的问题。简单来说，它定义了方法之间事务边界的规则，决定了是加入现有事务、创建一个新事务，还是以非事务方式运行。

Spring 在 `Propagation` 枚举类中定义了 7 种传播行为，我们可以根据它们的特性将其分为三类来理解：

一、核心分类与行为详解

1. 支持当前事务（最常用的类别）

这类行为倾向于融入现有的事务环境。

+ REQUIRED（默认行为）：这是最常用的选项。如果被调用方法当前存在事务，它就加入该事务；如果当前没有事务，它就创建一个新事务。这保证了操作要么在同一个事务中一起提交/回滚，要么独立运行。
+ SUPPORTS：如果当前存在事务，它就加入；如果当前没有事务，它就以非事务方式执行。这通常用于查询操作，既能利用事务的一致性，又能在非事务场景下避免开销。
+ MANDATORY：强制要求当前必须存在事务，否则就抛出异常。这通常用于作为其他事务一部分的内部逻辑，防止被独立调用。

1. 不支持当前事务（挂起或禁止）

这类行为倾向于脱离现有的事务环境。

+ REQUIRES_NEW：无论当前是否存在事务，它都会挂起当前事务并创建一个全新的独立事务。新事务的提交或回滚不会影响外部事务，常用于记录日志或审计信息，确保即使主业务回滚，日志也能保存。
+ NOT_SUPPORTED：以非事务方式执行，如果当前存在事务，则将其挂起。适用于耗时的、不需要事务支持的只读操作。
+ NEVER：以非事务方式执行，如果当前存在事务，则抛出异常。

1. 嵌套事务（特殊的子事务）

+ NESTED：如果当前存在事务，它会在当前事务中创建一个嵌套事务（保存点）；如果当前没有事务，则行为等同于 `REQUIRED`。嵌套事务可以独立回滚到保存点而不影响外部事务，但它的最终提交依赖于外部事务。

二、7种传播行为速查表

| 分类 | 传播行为 | 当前有事务时 | 当前无事务时 |
| :--- | :--- | :--- | :--- |
| 支持当前事务 | REQUIRED(默认) | 加入当前事务 | 创建新事务 |
| | SUPPORTS | 加入当前事务 | 非事务执行 |
| | MANDATORY | 加入当前事务 | 抛出异常 |
| 不支持当前事务 | REQUIRES_NEW | 挂起当前事务，创建新事务 | 创建新事务 |
| | NOT_SUPPORTED | 挂起当前事务，非事务执行 | 非事务执行 |
| | NEVER | 抛出异常 | 非事务执行 |
| 嵌套事务 | NESTED | 创建嵌套事务（保存点） | 创建新事务 |

三、关键区别与选型建议

在实际开发中，最容易混淆的是 `REQUIRED`、`REQUIRES_NEW` 和 `NESTED`。

+ 首选 REQUIRED：在绝大多数业务场景下（如订单创建同时扣减库存），使用默认的 `REQUIRED` 即可，它能保证一系列操作在同一个事务中原子性地完成。
+ 需要独立提交用 REQUIRES_NEW：当你需要子操作不受外部事务回滚影响时（如记录操作日志），应使用 `REQUIRES_NEW`。它与外部事务是完全独立的。
+ 需要部分回滚用 NESTED：当你希望子操作失败时只回滚它自己，而不影响外部事务的其他操作时，可以使用 `NESTED`。它依赖于数据库的保存点（Savepoint）机制，比 `REQUIRES_NEW` 更轻量，但它的提交最终依赖于外部事务。

### 41. sleep()和wait()的区别？

`sleep()` 和 `wait()` 虽然看起来都是让线程“暂停”执行，但它们的设计初衷、底层机制以及对锁的处理方式完全不同。简单来说，`sleep()`是线程的“自我休眠”，抱着锁睡觉；而`wait()`是线程间的“协作等待”，会主动释放锁。

以下是它们的核心区别：

一、核心区别：锁的释放（最关键点）

+ `sleep()`不释放锁：当线程调用 `sleep()` 时，它只是暂停执行，依然持有当前获得的所有对象锁。如果其他线程想访问该对象的同步代码块，必须等待 `sleep()` 结束。
+ `wait()`释放锁：当线程调用 `wait()` 时，它会立即释放当前持有的对象锁，并进入等待队列。这允许其他线程获取该锁并修改共享数据，从而为唤醒当前线程创造条件。

二、归属与调用方式

+ `sleep()`：是 `Thread`类的静态方法。它作用于当前正在执行的线程，可以在任何地方调用，不需要依赖同步代码块。
+ `wait()`：是 `Object`类的实例方法。它必须通过对象实例调用（如 `obj.wait()`），且必须在同步代码块（`synchronized`）或同步方法中调用，否则会抛出 `IllegalMonitorStateException` 异常。

三、唤醒机制

+ `sleep()`：时间到了自动唤醒。它需要传入一个时间参数（毫秒），时间一到线程就会自动恢复运行（变为就绪状态，等待 CPU 调度）。
+ `wait()`：需要被动唤醒。调用 `wait()` 后，线程会一直等待，直到其他线程调用同一个对象的 `notify()` 或 `notifyAll()` 方法将其唤醒，或者设置了超时时间（`wait(long timeout)`）后自动醒来。

四、总结对比表

| 特性 | `sleep()` | `wait()` |
| :--- | :--- | :--- |
| 所属类 | `Thread`<br/>类（静态方法） | `Object`<br/>类（实例方法） |
| 锁的行为 | 不释放锁（抱着锁睡） | 释放锁（让出资源） |
| 调用前提 | 任意位置均可 | 必须在 `synchronized`<br/> 块中 |
| 唤醒方式 | 时间到自动唤醒 | 需 `notify()`<br/> / `notifyAll()`<br/> 唤醒 |
| 使用场景 | 模拟耗时、暂停执行、轮询间隔 | 线程间通信、等待条件满足 |

五、场景建议

+ 如果你只是想让程序暂停一下（例如模拟网络延迟、定时轮询），或者不需要涉及多线程之间的数据交互，请使用 `sleep()`。
+ 如果你是在处理多线程协作问题（例如生产者-消费者模型），需要线程 A 等待线程 B 完成某个操作后再继续，请使用 `wait()` 配合 `notify()`。

### 42. chmod 644表示什么？具体而言6表示什么？为什么有3个数字？

`chmod 644` 是 Linux 系统中一种非常标准的文件权限设置，通常用于普通文件（如文本、配置文件、图片等），其核心含义是：“所有者可读写，其他人只读”。

一、为什么有 3 个数字？

这 3 个数字分别对应 Linux 权限模型中的三类用户角色：

1. 所有者 (User/Owner)：文件的创建者或当前拥有者。
2. 所属组 (Group)：文件所属的用户组，组内的成员共享该组的权限。
3. 其他用户 (Others)：既不是所有者，也不在所属组内的其他所有用户。

二、数字“6”表示什么？

Linux 权限使用八进制数字来代表权限组合，其基础规则是：读(r)=4，写(w)=2，执行(x)=1。

+ 数字 6：是 4 (读) + 2 (写) 的和。因此，它代表读和写的权限 (`rw-`)。
+ 在 `644` 中，第一个数字 `6` 就是指文件所有者拥有读和写的权限。

三、`chmod 644`的完整解读

将三个数字拆解来看，`644` 的权限分配如下：

| 数字 | 对应角色 | 权限组合 (r+w+x) | 符号表示 | 含义 |
| :--- | :--- | :--- | :--- | :--- |
| 6 | 所有者 (User) | 4 (读) + 2 (写) | `rw-` | 所有者可以查看和修改文件。 |
| 4 | 所属组 (Group) | 4 (读) | `r--` | 同组用户只能查看文件，不能修改。 |
| 4 | 其他用户 (Others) | 4 (读) | `r--` | 其他用户也只能查看文件，不能修改。 |

一句话总结：`chmod 644` 是一种兼顾安全与共享的权限设置，它允许文件所有者进行编辑，同时确保所有其他用户（包括同组和其他人）都只能读取，无法篡改内容。

### 43. 如何查看linux磁盘空间使用率？

在 Linux 系统中，查看磁盘空间使用率主要依赖两个核心命令：`df` 和 `du`。它们分工明确，通常结合使用来快速定位磁盘问题。

简单来说，`df`用于宏观查看整个文件系统的剩余空间，而`du`用于微观分析具体目录或文件的大小。

以下是查看磁盘空间的关键点概括：

一、`df`命令：查看整体磁盘使用情况

`df` (disk free) 命令用于显示文件系统的磁盘空间使用情况，包括总容量、已用空间、可用空间和挂载点等信息。

+ 常用参数：

+ `-h`：以人类可读的格式显示（如 GB、MB），这是最常用的参数。
+ `-i`：查看 inode 的使用情况。有时磁盘空间未满，但 inode 耗尽也会导致无法创建新文件。
+ `-T`：显示文件系统的类型（如 ext4, xfs）。

+ 示例：

```plain
df -h
```

这个命令会列出所有已挂载分区的空间使用率，让你一眼看出哪个分区（如 `/` 或 `/data`）空间紧张。

二、`du`命令：分析具体目录/文件占用

`du` (disk usage) 命令用于估算文件和目录的磁盘使用量，是查找“谁占用了空间”的利器。

+ 常用参数：

+ `-h`：以人类可读的格式显示大小。
+ `-s`：仅显示总计，不列出子目录的详细信息。
+ `--max-depth=N`：指定查看目录的层级深度，例如 `--max-depth=1` 只看当前目录下的一级子目录大小。

+ 示例：

```plain
# 查看当前目录下各个文件和文件夹的大小
du -h --max-depth=1

# 查看指定目录的总大小
du -sh /var/log
```

三、进阶技巧与可视化

除了基础命令，还有一些技巧可以帮助你更高效地管理磁盘：

+ 查找大文件：结合 `du`、`sort` 和 `head` 命令，可以快速找出占用空间最大的文件或目录。

```plain
# 找出根目录下最大的10个目录
du -h --max-depth=1 / | sort -hr | head -10
```

+ 交互式工具`ncdu`：这是一个基于终端的图形化工具，可以交互式地浏览和分析磁盘使用情况，比 `du` 更直观。
+ 注意 `df` 与 `du` 结果不一致：如果 `df` 显示磁盘已满，但 `du` 统计的总大小却不大，很可能是因为有文件已被删除，但仍有进程在占用它（如日志文件），导致空间未被释放。此时需要重启相关进程来释放空间。

### 44. 介绍一下Java的异常体系？平时编码的时候遇到的常见异常？

Java 的异常体系是一个清晰、层次分明的类继承结构，所有异常和错误都源自顶层父类 `java.lang.Throwable`。理解这个体系是编写健壮、可维护代码的基础。

一、异常体系总览

`Throwable` 类之下分为两个主要分支：`Error` 和 `Exception`。

+ `Error`(错误)
代表 JVM 层面的严重问题，通常是应用程序无法处理或恢复的。例如 `OutOfMemoryError` (内存溢出) 和 `StackOverflowError` (栈溢出)。这类错误一般由 JVM 抛出，我们编码时无需也无法处理，重点在于通过优化配置和代码来规避。
+ `Exception`(异常)
代表程序本身可以预见并处理的异常情况，是开发中需要重点关注的部分。它又进一步分为两大类：

 1. 受检异常 (Checked Exception)：编译器会强制检查。如果方法可能抛出此类异常，必须通过 `try-catch` 捕获处理，或者使用 `throws` 声明抛出。典型的例子是 `IOException` (IO操作异常) 和 `SQLException` (数据库操作异常)。
 2. 运行时异常 (Runtime Exception / Unchecked Exception)：编译器不强制检查。这类异常通常由程序逻辑错误导致，是日常开发中最常遇到的“Bug”。

二、常见运行时异常

运行时异常种类繁多，以下是编码时最常遇到的几种：

+ `NullPointerException`(空指针异常)：当尝试访问一个为 `null` 的对象的方法或属性时发生。这是 Java 中最臭名昭著的异常。
+ `ArrayIndexOutOfBoundsException`(数组越界异常)：访问数组时使用了非法的索引（小于0或大于等于数组长度）。
+ `ClassCastException`(类型转换异常)：在运行时，试图将一个对象强制转换为不兼容的类型。
+ `ArithmeticException`(算术异常)：例如，进行非法的算术运算，如整数除以零。
+ `IllegalArgumentException`(非法参数异常)：向方法传递了不合法或不正确的参数。
+ `NumberFormatException`(数字格式化异常)：在尝试将字符串转换为数字（如 `Integer.parseInt("abc")`）时，字符串格式不正确。

三、核心区别与最佳实践

| 类别 | 关键特征 | 处理策略 |
| :--- | :--- | :--- |
| 受检异常 | 编译期强制处理，通常是外部资源问题（如文件、网络）。 | 必须`try-catch`<br/>或 `throws`<br/>，进行合理的兜底处理。 |
| 运行时异常 | 编译期不检查，通常是程序逻辑缺陷。 | 重点在于预防，通过判空、参数校验、边界检查等从根源避免。 |

在编码实践中，应遵循以下原则：

1. 精准捕获：`catch` 块应尽可能捕获具体的异常类型，避免使用 `catch (Exception e)` 这种过于宽泛的写法，以便于问题定位。
2. 切勿吞掉异常：捕获异常后，至少要记录日志，绝不能留一个空的 `catch` 块，否则会导致问题难以排查。
3. 优先预防：对于运行时异常，应通过严谨的代码逻辑（如使用 `Optional`、检查索引等）来预防，而不是依赖 `try-catch`。

### 45. volatile关键字的作用？为什么能保证可见性和有序性？为什么不能保证原子性？

`volatile` 是 Java 提供的一种轻量级同步机制，它的主要作用是保证多线程环境下变量的可见性和有序性，但它不能保证原子性。

一、为什么能保证可见性和有序性？

`volatile` 的这两个特性是通过底层的内存屏障 (Memory Barrier) 和 MESI 缓存一致性协议实现的。

1. 保证可见性
当一个线程修改了 `volatile` 变量的值，JVM 会立即将这个新值刷新回主内存，并通知其他 CPU 核心，使它们缓存中该变量的副本失效。这样，当其他线程需要读取这个变量时，就不得不从主内存中重新加载最新的值，从而保证了所有线程看到的都是最新数据。这个过程依赖于 CPU 的 MESI 协议来维护缓存一致性。
2. 保证有序性
编译器和处理器为了优化性能，常常会对指令进行重排序。`volatile` 通过在读写操作前后插入特定的内存屏障指令，来禁止特定类型的指令重排。

+ 写操作时：在 `volatile` 写之前插入 `StoreStore` 屏障，保证之前的所有写操作都已完成；在写之后插入 `StoreLoad` 屏障，保证本次写操作完成后，后续的操作才能开始。
+ 读操作时：在 `volatile` 读之前插入 `LoadLoad` 屏障，保证读操作完成后，后续的读操作才能开始；在读之后插入 `LoadStore` 屏障，保证后续的写操作不会重排到本次读操作之前。
通过这种方式，`volatile` 确保了其读写操作的顺序性，防止了乱序执行。

二、为什么不能保证原子性？

原子性是指一个或多个操作要么全部执行成功，要么全部不执行，是一个不可分割的整体。`volatile` 无法保证复合操作的原子性。

最经典的例子就是 `count++` 操作。这个看似简单的操作，实际上包含了三个独立的步骤：

1. 读取 (Read)：从主内存中读取 `count` 的当前值。
2. 修改 (Modify)：在工作内存中对读取的值进行 `+1` 运算。
3. 写入 (Write)：将运算后的新值写回主内存。

即使 `count` 是 `volatile` 变量，也只能保证这三个步骤中每一步的可见性和有序性。当多个线程同时执行 `count++` 时，它们可能同时读取到同一个旧值，然后各自加 1，再写回主内存，导致最终结果比预期要小。因为 `volatile` 是一种无锁机制，无法像 `synchronized` 那样提供排他性，来确保整个“读-改-写”过程的原子性。

三、总结与适用场景

| 特性 | `volatile`<br/>是否保证 | 原因简述 |
| :--- | :--- | :--- |
| 可见性 | ✅保证 | 强制刷新到主内存，并使其他线程缓存失效。 |
| 有序性 | ✅ 保证 | 通过内存屏障禁止指令重排序。 |
| 原子性 | ❌ 不保证 | 无法保证“读-改-写”等复合操作的不可分割性。 |

适用场景：

+ 状态标记位：如一个 `volatile boolean stopFlag`，一个线程修改它，多个线程根据它决定是否停止。
+ 双重检查锁定 (DCL) 单例模式：防止对象初始化时的指令重排序，避免其他线程获取到“半初始化”的对象。
+ 与 CAS 结合：在 `java.util.concurrent.atomic` 包下的原子类中，`volatile` 用于保证变量的可见性，而 CAS (Compare-And-Swap) 操作则负责保证原子性。

### 46. 秒杀场景下，如果没有redis，多个用户来抢单，大量的库存扣减的请求打在mysql上，这种情况下数据库压力大吗？会出现怎样的性能瓶颈？

在纯MySQL应对秒杀的场景下，数据库压力会极大，主要瓶颈集中在：连接数耗尽、锁竞争激烈和磁盘I/O瓶颈。瞬间高并发会导致数据库连接池被打满，大量线程阻塞；而库存扣减通常基于`SELECT ... FOR UPDATE`或乐观锁实现，高频更新同一行数据会造成严重的行级锁竞争，甚至大量事务超时或死锁。同时，磁盘I/O（写binlog、redo log）和CPU负载急剧上升，最终导致数据库响应飙升、请求大量超时，引发系统雪崩。因此，实践中必须引入Redis等中间件做前置缓存和请求削峰。

### 47. 这种场景下，会用到数据库的哪些锁？除了行锁，还会用到什么锁？

在秒杀场景下，MySQL 中主要会使用行级锁（Record Lock）来保证库存扣减的原子性，通常通过 `SELECT ... FOR UPDATE`或更新语句的排他锁实现。此外，在可重复读（RR）隔离级别下，为了防止幻读，InnoDB 还会使用间隙锁（Gap Lock）锁定索引项之间的间隙，但若库存更新基于主键或唯一索引的等值查询，则间隙锁影响较小。同时，事务在执行前会先获取意向锁（Intention Lock，如表级的 IX 锁）来协调行锁与表锁的冲突。高并发下，行锁竞争会引发大量事务阻塞和死锁检测开销，而间隙锁和意向锁的引入可能进一步加剧锁冲突，导致数据库吞吐量下降。

### 48. 介绍一下tcp粘包和拆包？

TCP 粘包和拆包是网络编程中一个非常经典的问题，其根源在于 TCP 协议是一种面向字节流的协议，它不保留应用层消息的边界。

简单来说，发送方发送的是一条条有明确意义的“消息”，但 TCP 只负责将这些消息看作一串没有边界的“字节流”进行传输。这就像一条传送带，发送方放上去的是一杯杯水，但接收方拿到的可能是一桶混合在一起的水，或者一杯水分成了好几次才拿到。

一、什么是粘包和拆包？

+ 粘包 (Sticky Packet)：发送方连续发送的多个小数据包，在接收方被一次性读取，合并成了一个大数据包。接收方无法区分原始消息的边界。
+ 拆包 (Split Packet)：发送方发送的一个大数据包，在传输过程中被 TCP 协议栈切分成多个小数据包，导致接收方需要多次读取才能拼凑出完整的消息。

二、为什么会发生？

主要原因可以归结为以下几点：

1. 协议本质：TCP 的设计目标是可靠、有序地传输字节流，它不关心应用层消息的含义和边界。
2. 发送方原因：

+ Nagle 算法：为了优化网络效率，TCP 默认开启 Nagle 算法，它会将短时间内发送的多个小数据包合并成一个大包发送，这容易导致粘包。
+ 数据过大：当应用层要发送的数据超过了 TCP 的最大报文段长度（MSS）时，TCP 协议栈会自动将其拆分成多个段发送，这导致了拆包。

1. 接收方原因：

+ 读取不及时：接收方应用层没有及时从系统内核的缓冲区读取数据，导致多个数据包在缓冲区中积压，一次读取就拿到了多个包。
+ 缓冲区限制：接收方一次 `recv()` 调用能读取的数据量有限，如果缓冲区中的数据超过这个量，就会分多次读取，可能导致一个完整的消息被拆开。

注意：UDP 协议是面向消息的，它会保留消息的边界，因此不存在粘包和拆包的问题。

三、如何解决？

既然 TCP 本身不处理消息边界，我们就必须在应用层设计自己的协议来解决。以下是几种主流方案：

| 解决方案 | 原理 | 优点 | 缺点 | 适用场景 |
| :--- | :--- | :--- | :--- | :--- |
| 固定长度 | 每条消息都规定为固定的字节长度。 | 实现简单，解析高效。 | 浪费带宽（短消息需填充），不灵活（无法处理超长消息）。 | 传输格式固定的数据，如某些传感器数据。 |
| 特殊分隔符 | 在每条消息的末尾添加特殊字符（如 `\n`<br/>, `\r\n`<br/>）作为结束标记。 | 协议直观，消息长度可变。 | 消息内容本身不能包含分隔符，否则需要复杂的转义机制。 | 文本协议，如 HTTP、Redis 协议。 |
| 消息头+长度字段 | 在消息头部加入一个固定长度的字段，用来标识消息体的长度。 | 灵活、高效、无歧义，是工业界最主流的方案。 | 实现相对复杂，需要精确控制字节的读写。 | 绝大多数自定义的私有协议，如 RPC、游戏、即时通讯。 |

一句话总结：TCP 粘包和拆包不是 TCP 的缺陷，而是其流式特性的必然结果。解决这个问题的关键在于在应用层协议中明确定义消息的边界。

### 49. 介绍一下http 1/2/3，http2.0和http3.0的主要区别？

HTTP 协议的演进是一部为了解决“快”和“稳”而不断重构的历史。从 HTTP/1 到 HTTP/3，核心目标始终是降低延迟、提升传输效率。

简单来说，HTTP/1 是“串行且简陋的”，HTTP/2 解决了“应用层的拥堵”但受限于底层传输，而 HTTP/3 则彻底“换掉了底层传输协议”，实现了真正的无阻塞传输。

以下是 HTTP 1/2/3 的演变关键点及 HTTP/2 与 HTTP/3 的核心区别：

一、HTTP/1.x：由于“排队”导致的拥堵

HTTP/1.0 和 1.1 是互联网的基石，但它们存在明显的性能瓶颈：

+ 短连接与长连接：HTTP/1.0 每次请求都要建立一次 TCP 连接，开销巨大。HTTP/1.1 引入了 `Keep-Alive`（长连接），允许在一个连接上发送多个请求，但这只是缓解了连接建立的开销。
+ 队头阻塞 (Head-of-Line Blocking)：这是 HTTP/1.x 最大的痛点。在同一个 TCP 连接中，请求必须按顺序处理。如果第一个请求（比如一张大图）处理慢，后面的请求（比如 CSS/JS）必须等待，导致页面加载卡顿。虽然浏览器通过“域名分片”（同时开 6-8 个连接）来绕过这个问题，但这增加了服务器压力。

二、HTTP/2.0：多路复用，解决应用层阻塞

HTTP/2 是基于 TCP 的一次重大升级，它通过二进制分帧彻底改变了数据传输方式：

+ 多路复用 (Multiplexing)：这是 HTTP/2 的核心。它将 HTTP 消息拆分为独立的二进制帧，可以在同一个 TCP 连接上并行交错发送多个请求和响应。这解决了 HTTP/1.1 的应用层队头阻塞，浏览器不再需要域名分片。
+ 头部压缩 (HPACK)：HTTP/1 的头部是纯文本，重复且占用带宽。HTTP/2 使用 HPACK 算法压缩头部，大幅减少了传输量。
+ 遗留问题：虽然 HTTP/2 解决了应用层的阻塞，但它底层依然依赖 TCP。TCP 是可靠的流协议，如果传输过程中丢失了一个 TCP 数据包，整个 TCP 连接的所有流都必须等待重传。这被称为TCP 层的队头阻塞，在弱网（高丢包率）环境下，HTTP/2 的性能提升会大打折扣。

三、HTTP/3.0：抛弃 TCP，基于 UDP 的彻底重构

HTTP/3 是为了解决 HTTP/2 在弱网环境下的 TCP 队头阻塞问题而生的，它不再使用 TCP，而是基于 Google 开发的 QUIC 协议（运行在 UDP 之上）：

+ 彻底解决队头阻塞：QUIC 在应用层实现了自己的可靠传输。每个流（Stream）是独立的，丢包只会影响当前的流，不会阻塞同一连接下的其他流。
+ 极速建连 (0-RTT/1-RTT)：TCP 建立连接需要三次握手，加上 TLS 加密握手通常需要 3 个往返。HTTP/3 将加密和传输握手合并，通常只需 1 个往返，甚至支持 0-RTT 恢复连接，大幅降低了首屏延迟。
+ 连接迁移：TCP 连接由四元组（源/目 IP，源/目端口）标识，网络切换（如 WiFi 切 4G）会导致 IP 变化，连接断开。HTTP/3 使用 Connection ID 标识连接，网络切换时连接依然保持，无需重连。

四、HTTP/2.0 与 HTTP/3.0 的主要区别

这是目前最关键的对比，主要体现在底层协议和抗弱网能力上：

| 核心维度 | HTTP/2.0 | HTTP/3.0 |
| :--- | :--- | :--- |
| 底层协议 | TCP+ TLS | UDP(基于 QUIC) + TLS 1.3 |
| 队头阻塞 | 存在 (TCP 层丢包会阻塞所有流) | 彻底解决 (流独立，丢包仅影响当前流) |
| 连接建立 | 较慢 (TCP 握手 + TLS 握手) | 极快 (合并握手，支持 0-RTT) |
| 网络切换 | 不支持 (IP 变化需重新握手) | 支持 (基于 Connection ID 平滑迁移) |
| 头部压缩 | HPACK | QPACK (优化了 HPACK 在 QUIC 上的阻塞问题) |
| 适用场景 | 稳定网络环境下的高并发 Web 应用 | 移动网络、弱网环境、实时音视频、跨国传输 |

总结：

+ HTTP/1.1：简单，但并发性能差。
+ HTTP/2：在光纤、WiFi 等优质网络下性能极佳，是目前的主流。
+ HTTP/3：在 4G/5G、跨国、高丢包率的弱网环境下表现卓越，是未来的趋势。

### 50. 介绍一下CopyOnWriteArrayList的原理？使用时需要加锁吗？

`CopyOnWriteArrayList` 是 Java 中一种特殊的线程安全列表，其核心设计思想是 “写时复制” (Copy-On-Write, COW)。它通过牺牲写操作的性能和增加内存开销，来换取读操作的极致高效，因此特别适合读多写少的高并发场景。

一、核心原理：写时复制

`CopyOnWriteArrayList` 的内部实现基于一个 `volatile` 修饰的数组和一个 `ReentrantLock`。

1. 读操作（无锁）：当执行 `get()` 等读取操作时，线程会直接访问内部的 `volatile` 数组。由于数组是 `volatile` 的，任何写操作对数组引用的修改对所有读线程都是立即可见的，因此读操作完全不需要加锁，性能极高。
2. 写操作（加锁+复制）：当执行 `add()`、`remove()` 等修改操作时，流程如下：

+ 加锁：首先获取 `ReentrantLock`，确保同一时间只有一个线程能进行写操作。
+ 复制：将当前的旧数组完整地复制一份，生成一个新数组。
+ 修改：在新数组上执行实际的增删改操作。
+ 替换：将内部 `volatile` 数组的引用指向这个新数组。
+ 解锁：释放锁。

这个过程就像修改一份共享文档时，不是直接在原文档上改，而是复印一份，在复印件上修改，修改完成后再用新文档替换掉旧文档。

二、使用时需要加锁吗？

不需要。

`CopyOnWriteArrayList` 将所有同步控制都封装在了其内部实现中。无论是读操作的无锁访问，还是写操作的加锁复制，都对调用者透明。你在使用它时，就像使用普通的 `ArrayList` 一样，无需任何额外的同步措施（如 `synchronized` 或 `ReentrantLock`）。

三、关键特性与适用场景

| 特性 | 说明 |
| :--- | :--- |
| 线程安全 | 内部通过写时复制和锁机制保证线程安全。 |
| 读性能极高 | 读操作无锁，并发读取效率非常高。 |
| 写性能较差 | 每次写都需复制整个数组，时间和内存开销大，不适合写频繁的场景。 |
| 弱一致性 | 读操作可能读到旧数据，因为写操作替换数组引用需要时间。 |
| 迭代器安全 | 迭代器基于创建时的数组快照，遍历时不会抛出 `ConcurrentModificationException`<br/>。 |

适用场景：

+ 读多写少：例如白名单/黑名单列表、系统配置信息、监听器列表等。
+ 高并发读：需要极致的读取性能，且能容忍短暂的数据不一致。

不适用场景：

+ 写操作频繁：频繁的数组复制会导致性能急剧下降。
+ 数据量巨大：复制大数组会消耗大量内存，可能引发 `OutOfMemoryError`。
+ 强一致性要求：如金融交易等场景，不能接受读取到过期数据。

### 51. Synchronized修饰静态方法和普通方法的区别是什么？

`synchronized` 修饰静态方法和普通方法（实例方法）的核心区别在于 锁的对象不同，这直接决定了它们的同步范围和互斥行为。

简单来说，普通方法锁住的是“当前实例”，而静态方法锁住的是“整个类”。

一、锁的对象不同

+ 修饰普通方法（实例锁）
当 `synchronized` 修饰一个普通方法时，它锁定的是调用该方法的当前实例对象（`this`）。

+ 效果：当一个线程进入某个对象的同步方法时，其他线程无法访问同一个对象的任何其他 `synchronized` 方法。
+ 并发：由于每个对象实例都有自己独立的锁，因此多个线程可以同时访问不同实例的 `synchronized` 方法，它们之间互不干扰。

+ 修饰静态方法（类锁）
当 `synchronized` 修饰一个静态方法时，它锁定的是当前类的 `Class` 对象（例如 `MyClass.class`）。

+ 效果：当一个线程进入该类的静态同步方法时，其他线程无法访问该类的任何其他 `synchronized static` 方法。
+ 并发：由于一个类在 JVM 中只有一个 `Class` 对象，所以这把锁是全局唯一的。无论创建多少个实例，所有线程在调用该类的静态同步方法时，都必须竞争同一把锁，因此只能串行执行。

二、互斥关系与使用场景

+ 互斥关系
实例锁和类锁是两把完全独立的锁。一个线程在执行 `synchronized` 实例方法，另一个线程可以同时执行 `synchronized` 静态方法，它们之间不会互相阻塞。
+ 使用场景

+ 实例锁：用于保护实例变量的线程安全，确保同一实例的状态在多线程环境下不被破坏。
+ 类锁：用于保护静态变量或类级别的共享资源的线程安全，因为静态变量是所有实例共享的。

三、总结对比

| 特性 | `synchronized`<br/>修饰普通方法 | `synchronized`<br/>修饰静态方法 |
| :--- | :--- | :--- |
| 锁对象 | 当前实例对象 (`this`<br/>) | 当前类的`Class`<br/>对象 (`MyClass.class`<br/>) |
| 同步范围 | 控制同一实例的并发访问 | 控制整个类的并发访问 |
| 互斥性 | 不同实例之间互不干扰 | 全局互斥，所有实例共享一把锁 |
| 适用场景 | 保护实例变量 | 保护静态变量 |

### 52. 解释一下索引下推？联合索引是abc，查询条件只有ac，会触发索引下推吗？

索引下推（Index Condition Pushdown, ICP）是 MySQL 5.6 引入的一项重要查询优化。它的核心思想是将原本由 Server 层处理的过滤条件，下推到存储引擎层，利用索引中的字段提前进行过滤，从而减少不必要的回表操作。

简单来说，就是“就地取材，提前过滤”。在没有 ICP 时，存储引擎层只能根据联合索引的最左前缀找到大致范围的索引项，然后全部回表取出完整行数据，再交给 Server 层进行后续条件的判断。而有了 ICP，存储引擎层在扫描索引时，就可以直接利用索引中已有的字段值来判断 WHERE 条件，只有满足所有条件的索引项才会触发回表，大大降低了磁盘 I/O 和 CPU 开销。

一、针对 `联合索引(abc)`，查询 `a` 和 `c` 会触发索引下推吗？

会的，这正是索引下推的典型应用场景。

对于联合索引 `(a, b, c)`，当查询条件为 `WHERE a = ? AND c = ?` 时：

1. 遵循最左前缀原则：查询会首先利用索引中的 `a` 列来快速定位到满足 `a = ?` 条件的索引记录范围。
2. 触发索引下推：由于索引 `(a, b, c)` 的叶子节点中包含了 `a`、`b`、`c` 三个字段的值，存储引擎在扫描到满足 `a = ?` 的记录后，不会立即回表，而是会直接读取索引中 `c` 字段的值，判断其是否满足 `c = ?` 的条件。
3. 减少回表：只有当 `a` 和 `c` 的条件都满足时，存储引擎才会拿着这条索引记录的主键 ID 去回表查询完整的行数据。

这个过程避免了为那些 `a` 匹配但 `c` 不匹配的记录进行无意义的回表操作，显著提升了查询效率。

二、如何验证索引下推是否生效？

你可以通过 `EXPLAIN` 命令来查看 SQL 的执行计划。如果 `Extra` 字段中出现了 `Using index condition`，就说明查询触发了索引下推优化。

三、触发索引下推的关键条件

+ 存储引擎：必须是 InnoDB 或 MyISAM。
+ 索引类型：必须是联合索引（二级索引）。单列索引无法触发 ICP。
+ 查询条件：查询中必须包含索引中的字段，并且这些字段不能全部用于索引查找（例如，由于范围查询导致最左前缀原则中断，后续索引列的条件就可以通过 ICP 来过滤）。
+ 条件限制：下推的条件必须是简单的列值比较，不能是函数、子查询等存储引擎无法直接计算的表达式。

### 53. Redis用set实现分布式锁，过期时间的值设置为多少？如果内存里面有几千万个key，如何快速定位想要查询的key？

针对你提出的两个关于 Redis 的核心问题，我为你整理了详细的解答：

1. Redis 分布式锁的过期时间设置

设置分布式锁的过期时间（TTL）是防止死锁的关键机制，但设置多少并没有一个绝对的“标准值”，而是需要根据业务场景来权衡。

+ 基本原则：过期时间应略大于业务逻辑执行的最大预估时间。

+ 通常建议设置为业务平均耗时的 2-3 倍。例如，如果业务操作通常耗时 200ms，可以将锁的过期时间设置为 1秒。
+ 对于一般的短任务，通常设置在 10秒 到 30秒 之间。

+ 进阶方案：看门狗（Watchdog）机制

+ 如果业务执行时间不确定（可能很长），单纯设置一个固定时间很难平衡：设短了业务没跑完锁就失效（导致并发问题），设长了服务挂了恢复慢。
+ 推荐做法：使用 Redisson 等客户端库提供的 Watchdog 机制。它会在获取锁成功后，在后台启动一个定时线程（通常每 10秒），自动给锁“续期”（重置过期时间），只要业务线程还在运行，锁就不会过期。

1. 几千万 Key 中快速定位查询

当 Redis 内存中有几千万甚至上亿个 Key 时，定位特定 Key 的策略取决于你是要“精确查找”还是“模糊匹配”。

场景 A：模糊查询（例如查找所有 `user:100*` 开头的 Key）

这是最棘手的场景，因为 Redis 是单线程的，错误的命令会导致服务阻塞。

+ ❌绝对禁止：使用 `KEYS *` 命令。

+ 它会一次性遍历所有 Key，时间复杂度 O(N)。在几千万 Key 的数据量下，这会阻塞主线程数秒甚至更久，导致线上服务“雪崩”。

+ ✅标准方案：使用 `SCAN` 命令。

+ `SCAN` 是基于游标的迭代器，它分批次返回数据，不会一次性阻塞主线程。
+ 注意：虽然 `SCAN` 不阻塞，但在几千万数据量下遍历仍然消耗 CPU。建议在从节点（Slave）执行，或者在业务低峰期进行。

+ 🚀架构级优化：建立“索引表”（事前索引）。

+ 如果你需要频繁查询某类 Key（例如“所有 VIP 用户”），不要依赖扫描。
+ 做法：在写入数据时，同时维护一个 `Set` 或 `ZSet` 集合（例如 `index:vip_users`），将对应的 Key ID 存入其中。查询时直接 `SMEMBERS index:vip_users`，时间复杂度仅为 O(N)（N为结果集大小），速度极快。

场景 B：精确查询（已知完整的 Key 名称）

+ ✅极速定位：直接使用 `GET key_name`。

+ Redis 的底层是哈希表，精确查找的时间复杂度是 O(1)。即使有几千万个 Key，定位到一个具体的 Key 也是微秒级的，非常快。

总结对比表

| 需求场景 | 推荐方案 | 关键点 |
| :--- | :--- | :--- |
| 锁过期时间 | 业务耗时 x 2~3 倍 | 防止死锁，长任务建议用 Redisson 看门狗自动续期。 |
| 模糊查找 | `SCAN`<br/> 命令 | 严禁使用 `KEYS *`<br/>，生产环境建议通过维护 `Set`<br/> 集合做索引。 |
| 精确查找 | `GET`<br/> 命令 | O(1) 复杂度，几千万数据也能瞬间定位。 |

### 54. Redis的缓存淘汰策略介绍一下，是主动淘汰还是被动淘汰？

Redis 的缓存淘汰机制是一个复合策略，它通过过期删除和内存淘汰两种机制协同工作，在 CPU 消耗、内存利用率和数据一致性之间取得平衡。

简单来说，过期删除负责清理设置了过期时间的键，而内存淘汰则是在内存不足时，根据规则清理数据（包括未过期的键）以释放空间。

一、过期删除：主动与被动相结合

过期删除是 Redis 清理设置了过期时间（TTL）的键的核心机制。它并非采用单一的“主动”或“被动”方式，而是将两者结合，互为补充。

1. 被动删除：惰性删除 (Lazy Expiration)

+ 原理：这是一种“访问时检查”的策略。当客户端尝试访问一个键时，Redis 会先检查该键是否已过期。如果已过期，则立即删除它，并向客户端返回空值。
+ 优点：对 CPU 非常友好，只有在必须访问时才进行删除操作，不会消耗额外的计算资源。
+ 缺点：对内存不友好。如果一个过期键永远不被访问，它将永远占用内存，造成“内存泄漏”。

1. 主动删除：定期删除 (Periodic Expiration)

+ 原理：这是一种“后台巡逻”的策略。Redis 会周期性地（默认每秒 10 次）从所有设置了过期时间的键中，随机抽取一部分进行检查，并删除其中已过期的键。
+ 优点：能够主动清理那些长期未被访问的过期键，有效防止内存泄漏。
+ 缺点：由于采用随机抽样和时长限制（避免阻塞主线程），它无法保证清理所有过期键，仍会有少量残留。

协同工作：这两种策略共同构成了过期删除的闭环。定期删除作为主动巡逻，清理大部分“僵尸”过期键；惰性删除作为最后一道防线，确保任何被访问到的键都是有效的。

二、内存淘汰：内存不足时的最终防线

当 Redis 使用的内存达到 `maxmemory` 配置的上限时，即使过期删除机制也无法释放出足够空间，这时就会触发内存淘汰策略。它会根据预设的规则，主动淘汰一部分键（包括设置了过期时间和未设置的）来为新写入的数据腾出空间。

Redis 提供了多种内存淘汰策略，主要分为三类：

| 策略类别 | 策略名称 | 说明 |
| :--- | :--- | :--- |
| 不淘汰 | `noeviction`<br/>(默认) | 内存满时，拒绝所有写入请求并返回错误。 |
| 仅在易失键中淘汰 | `volatile-lru`<br/> / `volatile-lfu`<br/> / `volatile-random`<br/> / `volatile-ttl` | 只在设置了过期时间的键中，按照 LRU（最近最少使用）、LFU（最不经常使用）、随机或 TTL（剩余存活时间）等规则进行淘汰。 |
| 在所有键中淘汰 | `allkeys-lru`<br/> / `allkeys-lfu`<br/> / `allkeys-random` | 在所有键（无论是否设置过期时间）中，按照 LRU、LFU 或随机规则进行淘汰。 |

生产环境建议：如果将 Redis 用作纯缓存，推荐将策略设置为 `allkeys-lru` 或 `allkeys-lfu`，这样可以更有效地利用内存，自动淘汰旧数据。
