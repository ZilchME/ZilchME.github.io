在 MySQL 中，联合索引遵循**最左前缀原则**，很多人会有疑问：如果索引是 `(a,b,c)`，查询条件只用 `(b,c)`，还能利用索引吗？答案是**通常不能直接利用联合索引进行快速定位**，但有一些特殊情况可以降低查询成本。

本文就来总结几个关键技巧：**索引下推（ICP）、Index Skip Scan、以及通过补充前导列条件优化查询**。

## 1. 索引下推（Index Condition Pushdown, ICP）

假设有索引：

```sql
CREATE INDEX idx_abc ON t(a,b,c);
```

查询如下：

```sql
SELECT * FROM t WHERE b = 10 AND c = 20;
```

因为最左前缀 `a` 没有条件，MySQL 无法直接用 B+ 树快速定位到满足 `(b,c)` 的记录。但是，**索引下推**机制可以减少回表次数：

* MySQL 会扫描 `(a,b,c)` 索引，在索引层先判断 `b=10 AND c=20` 是否成立。
* 如果成立，再回表读取其他列。
* 这样可以避免对不满足条件的行访问聚簇索引（回表），降低 IO。

**注意**：ICP 并不是快速定位范围，而只是把过滤动作提前到了存储引擎层，减少无效回表，提高查询效率。

## 2. Index Skip Scan（索引跳跃扫描）

MySQL 8.0 的优化器支持**索引跳跃扫描**，适用于缺少联合索引最左列条件，但前导列基数较低的场景。

示例：

```sql
SELECT * FROM t WHERE b = 10 AND c = 20;
```

假设索引 `(a,b,c)`，而 `a` 的取值只有两个：`male` 和 `female`。优化器可以近似改写为：

```sql
WHERE a = 'male' AND b = 10 AND c = 20
UNION ALL
WHERE a = 'female' AND b = 10 AND c = 20;
```

* 每个小范围都能利用 `(a,b,c)` 的前缀索引进行快速定位。
* Skip Scan 的前提是**前导列基数低**，如果前导列 `a` 的不同值很多（如用户 ID、订单号），跳跃扫描成本会很高，优化器通常不会选用。

## 3. 通过补充前导列条件来利用索引

如果查询条件增加了前导列：

```sql
SELECT * FROM t WHERE a IN (1,2,3) AND b = 10 AND c = 20;
```

虽然 `a` 不是单个等值条件，但 `a IN (...)` 可以拆成多个等值范围：

```sql
WHERE a = 1 AND b = 10 AND c = 20
UNION ALL
WHERE a = 2 AND b = 10 AND c = 20
UNION ALL
WHERE a = 3 AND b = 10 AND c = 20;
```

* 每个小范围都能利用索引 `(a,b,c)` 的最左前缀。
* 复杂度从扫描全索引，变为对每个 `a` 值做索引范围查找。
* 前提是 `a in (...)` 数量不能太多，否则成本仍然高。

## 4. 总结

* 联合索引查询必须满足最左前缀原则，才能实现高效 B+ 树定位。
* 查询 `(b,c)` 时，通常无法直接利用 `(a,b,c)` 联合索引进行快速查找，但有几种特殊优化方式：

  1. **索引下推（ICP）**：提前在索引层过滤条件，减少回表。
  2. **Index Skip Scan**：前导列基数低时，优化器可跳跃扫描前导列取值，利用索引。
  3. **补充前导列条件**：通过 `a = ?` 或 `a IN (...)` 将前导列纳入查询条件，恢复联合索引的利用效率。
* 最优策略仍然是根据查询模式建立适合的索引，如 `(b,c)` 或 `(b,c,a)` 联合索引。
