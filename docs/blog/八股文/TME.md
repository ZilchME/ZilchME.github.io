## 讲一下进程、线程、协程

- 进程是操作系统资源分配的基本单位。每个进程有自己独立的地址空间、文件句柄、堆栈等资源，**进程之间相互隔离，所以稳定性好，但进程创建、销毁和切换的成本比较高**。进程间通信通常需要 IPC，比如管道、消息队列、共享内存、Socket 等。

- 线程是 CPU 调度的基本单位，也可以理解为进程内部的执行流。一个进程可以包含多个线程，**线程之间共享进程的内存空间和资源，比如堆、全局变量、文件句柄等，但每个线程有自己的栈和寄存器上下文**。线程比进程更轻量，切换成本更低，但**因为共享内存，所以需要考虑线程安全**，比如锁、原子操作、条件变量等。

- 协程是用户态的轻量级执行单元。它**不是由操作系统内核直接调度，而是由程序或运行时调度**。**==协程之间的切换通常发生在用户态==，不需要陷入内核，所以切换成本更低**。协程适合大量 I/O 密集型任务，比如网络请求、爬虫、异步服务等。但如果**遇到 CPU 密集型任务，单线程协程并不能真正并行**，需要结合多线程或多进程。

## TCP 第三次握手和第四次挥手的意义是什么

### TCP 三次握手

客户端发 `SYN`：客户端告诉服务端“我想建立连接，我的初始序列号是 x”。

服务端回 `SYN + ACK`：服务端告诉客户端“我收到了你的请求，我也想建立连接，我的初始序列号是 y”。

客户端再发 `ACK`：客户端告诉服务端“我收到了你的确认，也收到了你的初始序列号”。

第三次握手的关键作用是让服务端确认：**客户端能收到服务端的消息，客户端也能正常发送确认消息。**

如果只有两次握手，服务端收到客户端的 `SYN` 后就建立连接，但客户端可能根本没收到服务端的 `SYN + ACK`。这样服务端就会误以为连接建立成功，占用资源。

另外，第三次握手还可以避免“旧的 SYN 报文”导致服务端误建立连接。比如客户端之前发过一个连接请求，因为网络延迟很久才到服务端。如果只有两次握手，服务端可能直接建立一个无效连接；有第三次握手时，客户端不会对这个过期请求继续确认，连接就不会真正建立。

> 个人理解：三次握手目的是确认双方的收发能力，对于客户端，第收到二次握手后能确认自己的发送能力接收能力和服务端的接收能力发送能力，对于服务端，收到第一次握手能确认客户端的发送能力和自己的接收能力，收到第三次握手能确认自己的发送能力客户端的接收能力
>
> 经历三次握手后，双方才能均确认对方和自己的收发能力，此时连接才是可靠的
>
> 补充：三次握手不只是确认收发能力，还涉及 **同步双方的初始序列号 ISN**，并避免历史的、延迟到达的 `SYN` 报文导致服务端误建立连接

### TCP 四次挥手

主动关闭方发 `FIN`：表示“我这边数据发完了，准备关闭发送方向”。

被动关闭方回 `ACK`：表示“我知道你不发了”。

被动关闭方继续发送自己剩余的数据。

被动关闭方发 `FIN`：表示“我这边数据也发完了，也准备关闭”。

主动关闭方回 `ACK`：表示“我知道你也关闭了”。

第四次挥手的关键作用是确认对方的 `FIN`，告诉对方：**你的关闭请求我收到了，连接可以彻底结束了。**

为什么挥手通常需要四次？因为 TCP 是全双工的，双方的发送通道和接收通道是相互独立的。一方说“我不发了”，不代表另一方也发完了。所以第一次 `FIN` 只关闭一个方向，另一方需要先 `ACK`，等自己的数据发完后再发 `FIN`，最后由主动关闭方发第四次 `ACK`。

## MySQL 的 MVCC 是如何实现的

MySQL InnoDB 的 MVCC 是通过记录中的 `trx_id` 和 `roll_pointer` 维护 undo log 版本链，再通过 Read View 判断某个版本对当前事务是否可见。如果当前版本不可见，就沿版本链向前查找可见版本。**RC 隔离级别下每次查询生成新的 Read View，RR 隔离级别下事务内复用第一次查询生成的 Read View**，因此可以实现一致性非锁定读和可重复读。

## 可重复读隔离级别下会加什么锁

会，但要分场景。**可重复读 RR 并不等于所有读都加锁**。在 MySQL InnoDB 里，普通 `SELECT` 通常走 MVCC 快照读，不加行锁；但是 `UPDATE / DELETE / INSERT`，以及 `SELECT ... FOR UPDATE`、`SELECT ... LOCK IN SHARE MODE` 这类当前读，会加锁。

普通查询：

```sql
select * from user where id = 1;
```

这是快照读。RR 下第一次普通查询生成 Read View，后续复用这个 Read View，所以能实现可重复读。它一般不加行锁，不阻塞其他事务修改。

当前读：

```sql
select * from user where id = 1 for update;

select * from user where id = 1 lock in share mode;

update user set name = 'A' where id = 1;

delete from user where id = 1;
```

这些需要读取最新版本的数据，并且为了保证接下来修改或判断条件的正确性，会加锁。

InnoDB 在 RR 下常见的锁主要有这些：

**共享锁，S 锁。**
也叫读锁。多个事务可以同时持有 S 锁，但 S 锁和 X 锁互斥。比如 `select ... lock in share mode` 会加共享锁。

**排他锁，X 锁。**
也叫写锁。`update`、`delete`、`select ... for update` 会加排他锁。X 锁之间互斥，X 锁也和 S 锁互斥。

**记录锁，Record Lock。**
锁住索引上的某一条记录。比如根据唯一索引等值命中一条记录：

```sql
update user set name = 'Tom' where id = 10;
```

如果 `id` 是主键或唯一索引，并且记录存在，通常就是锁住 `id = 10` 这一条索引记录。

**间隙锁，Gap Lock。**
锁住两个索引记录之间的间隙，不锁具体记录本身。它的作用主要是防止其他事务往这个范围里插入新记录，从而防止幻读。

比如表里有 `id = 10` 和 `id = 20`，执行：

```sql
select * from user where id > 10 and id < 20 for update;
```

可能会锁住 `(10, 20)` 这个间隙，阻止其他事务插入 `id = 15`。

**临键锁，Next-Key Lock。**
可以理解成 **记录锁 + 间隙锁**，锁住一个左开右闭区间，比如 `(10, 20]`。这是 InnoDB 在 RR 隔离级别下解决当前读幻读问题的核心锁机制。

范围查询时很常见：

```sql
select * from user where id >= 10 and id <= 20 for update;
```

InnoDB 会对扫描到的索引范围加 next-key lock，既锁住已有记录，也锁住记录之间的间隙，防止其他事务插入满足条件的新行。

**插入意向锁，Insert Intention Lock。**
这是插入数据前对 gap 加的一种特殊意向锁。它表示“我准备在这个间隙里插入一条记录”。多个事务如果插入的是同一个 gap 中不同位置，通常不互相阻塞；但如果这个 gap 被其他事务的 gap lock 或 next-key lock 锁住，就会等待。

> InnoDB 中的记录锁、间隙锁、临键锁和插入意向锁均是行锁的一种形式。记录锁锁住具体索引记录以防止脏写；间隙锁锁住索引间隙防止幻读；临键锁是记录锁加间隙锁组合，用于范围查询下防幻读；插入意向锁用于事务插入新记录时与其他行锁协调。

**意向锁，Intention Lock。**
这是表级锁，用来表示事务接下来想对表中的某些行加 S 锁或 X 锁。常见有 IS 锁和 IX 锁。它的作用是协调表锁和行锁之间的兼容关系。比如事务要给某些行加 X 锁之前，会先在表上加 IX 锁。

## MySQL中的覆盖索引

在 MySQL 中，**覆盖索引（Covering Index）** 是一个性能优化概念，面试经常考。核心意思是：**查询所需的所有列都包含在索引中，MySQL 不需要回表访问==主键聚簇记录==就能直接从索引返回结果。**
