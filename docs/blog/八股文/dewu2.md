本文围绕秒杀库存一致性、Java 并发加锁和 Redis 故障恢复三个问题展开。库存方案以 MySQL 为最终业务依据，Redis 用于流量拦截与库存预占；所有“请求处理中”的状态都需要有可恢复的记录。

## 一、秒杀系统如何保证 Redis 与数据库库存的最终一致性？

### 1. 先明确库存与成功的含义

**Redis 扣减表示预占，MySQL 条件扣减并提交订单事务，才表示下单成功。**异步受理后可以返回 `requestId` 和“排队中”，客户端再查询处理结果，不能把 Redis 预占成功直接显示为订单已经创建。

假设 Redis 可售库存和 MySQL 剩余库存最初均为 100：

| 阶段 | Redis 可售库存 | MySQL 剩余库存 | 请求状态 |
| --- | --- | --- | --- |
| 初始状态 | 100 | 100 | 无 |
| 预占 1 件，尚未落单 | 99 | 100 | PENDING |
| 落单成功并完成确认 | 99 | 99 | SUCCESS |
| 或者落单确定失败，完成回补 | 100 | 100 | FAILED |

成功后不再扣第二次 Redis；失败时回补的前提是数据库没有、并且后续也不会再为该请求提交订单。支付超时取消、退款等库存回补属于后续业务流程，同样需要幂等记录，不能与下单失败补偿重复计算。

### 2. 正常链路：预占、可靠任务、幂等落单、确认或补偿

1. **建立请求身份：**使用唯一 `requestId` 关联受理记录、消息、订单和库存操作。客户端重试同一业务请求时沿用它；限购约束则按活动、用户等实际业务粒度单独设计。
2. **原子预占：**使用 Lua 检查库存、限购及该请求是否已处理，在同次执行内扣减库存并记录预占状态。Redis Cluster 中脚本涉及的键必须满足同槽要求，键布局应提前设计。
3. **可靠任务投递：**使受理任务可持久化恢复，发送结果不确定时根据 `requestId` 查询、重试并去重，不能立即回补。仅在进程内记下“稍后重试”不足以应对进程崩溃。
4. **数据库落单：**消费者在同一本地事务范围内完成幂等状态检查、条件扣库存、订单创建和处理结果记录；提交后才确认消费。若订单、库存分属不同数据库或服务，应另外设计跨服务一致性与补偿，不能当作一个普通本地事务。
5. **确认或补偿：**成功后把 Redis 预占标为已完成；确定失败后，用 Lua 检查请求状态并只回补一次。消息重复消费或结果确认失败时，均应从持久化处理结果继续收敛。
6. **对账兜底：**扫描长期未完成的持久化任务，核对订单和库存流水，进行有限重试、终态确认或补偿，不能只扫描可能随 Redis 故障丢失的 PENDING 键。

条件扣库存可以写成：

```sql
UPDATE activity_stock
SET available_stock = available_stock - :quantity
WHERE activity_id = :activity_id
  AND sku_id = :sku_id
  AND available_stock >= :quantity;
```

`:quantity` 必须经过正数和购买上限校验。更新影响行数为 1 才表示本次扣减成功；为 0 时，应结合请求处理记录区分库存不足、记录不存在或已处理等情况。数据库中还需要 `requestId` 等业务唯一约束，避免重复消息再次扣库存。**条件更新保障库存不扣成负数，幂等保障同一业务请求不重复生效，两者不能互相替代。**

### 3. Redis 预占与 MQ 发送之间的空窗如何处理？

Redis Lua 与 MQ 发送不在同一本地事务中，存在以下故障窗口：

```text
Redis 预占成功 → 进程崩溃 → 消息尚未发送
```

如果只有 Redis 中的一条预占记录，恰好又发生 Redis 数据丢失，就无法仅凭 MQ 重试恢复这笔请求。需要根据系统的受理承诺选择方案：

- **持久化受理任务：**通过限流后的入口，将请求先可靠写入任务表或 MQ，再异步执行预占和落单。返回“已受理”前应满足约定的持久化确认条件。任务重复执行时使用相同 `requestId`，这会改变链路顺序与延迟，但避免已承诺受理的请求只存在于易失内存中。
- **受理记录与 Outbox：**若任务先写数据库，可以在同一事务内写受理记录与 Outbox [+Outbox]，再可靠投递消息。记录“待尝试”与“已成功预占”是不同状态，不能在尚未执行 Lua 时就将其记为预占成功。
- **Redis 内原子写入待处理流：**可以在脚本中预占并写入同槽的 Redis Stream，避免 Redis 操作与另一个系统发送之间的空窗；但它仍依赖 Redis 的持久化和复制，不能据此承诺 Redis 丢数据时请求零丢失。

不能先执行 Redis 再补写数据库记录，然后宣称“两边已经原子化”。是否接受未完成持久化前的预占丢失、是否承诺受理必达，需要在接口语义中明确。

### 4. 超时、取消与重复补偿如何避免冲突？

**超时只表示结果未知，不等于失败。**如果一边超时回补 Redis，另一边消费者稍后又提交订单，就可能把已卖出的库存重新放出。

可使用持久化请求状态机，由订单处理与取消流程对同一记录加锁或执行条件状态更新，串行决定终态。成功终态和失败终态不能同时成立；取消流程只有在确定该请求不再可能提交后才能回补。对于正在执行、提交结果不明的请求，应查询与重试确认，不能直接用“过期时间到了”裁定失败。

Redis 回补还需检查活动版本与请求状态，避免旧活动消息改到新活动库存；回补状态保留时间也应覆盖可能的重投和补偿窗口。补偿失败必须继续重试并告警，不能将“已发出补偿指令”直接当作已完成。

### 5. 对账时如何理解库存关系？

在本例不涉及取消、补货等其他库存变化，且采用同一业务截止点核对时，可理解为：

$$
\text{Redis 可售库存} + \text{尚未在 MySQL 生效的有效预占量}
= \text{MySQL 剩余库存}
$$

这里不能直接用“所有 PENDING 记录数”代替预占量：数据库可能已提交，只是 Redis 确认还未完成，此时不能重复扣除；购买数量大于 1 时也应按数量求和。在线读取两个系统还存在时间差，应结合处理流水、状态版本或受控对账窗口，避免误报。

**面试回答：**我会把 Redis 定义为预占库存，数据库作为最终业务依据，用唯一请求号串联持久化任务、幂等落单和补偿。Redis 预占与 MQ 发送之间没有天然事务，需要可靠受理记录或明确的数据丢失边界。数据库通过条件更新和唯一约束兜底，成功后确认预占，确定失败才回补，超时则先确认结果，最后通过对账闭环恢复遗漏。

## 二、Java 常用的加锁方式有哪些，各有什么特点和适用场景？

### 1. 先区分锁的作用范围

`synchronized` 和 `ReentrantLock` 等主要协调**同一个 JVM 中共享对象的线程**。多个服务实例即使执行相同代码，也不会自动共享同一把本地锁。涉及跨进程共享状态时，需要数据库约束、事务或分布式协调，不能只在 Controller 上加 `synchronized` 就认为全局安全。

### 2. 常用方式对比

| 方式 | 特点 | 适用场景与限制 |
| --- | --- | --- |
| `synchronized` | 可重入，进入和退出代码块自动获取、释放监视器锁，提供互斥与可见性 | 普通共享对象保护；等待获取锁本身不支持超时或中断式获取 |
| `ReentrantLock` | 可重入，支持 `tryLock`、可中断获取、公平策略和多个 Condition | 需要有界等待、取消或多种等待条件；必须在 `finally` 中解锁 |
| `ReentrantReadWriteLock` | 读锁共享、写锁独占，可重入 | 读多写少且受保护操作足够重时评估；不保证一定优于普通锁，避免持读锁直接等待写锁 |
| `StampedLock` | 支持写锁、读锁和需校验的乐观读，不可重入 | 愿意承担更复杂实现的读多写少场景；乐观读必须校验失败后重读 |
| 原子类 / CAS [+CAS] | 用原子读改写及重试完成部分并发操作，不是传统互斥锁 | 计数、状态转换等简单共享状态；高竞争下重试成本可能升高 |
| 数据库悲观锁 | 如事务内 `SELECT ... FOR UPDATE`，锁住所访问的记录或范围 | 跨应用实例的数据一致性；锁范围取决于 SQL、索引和隔离级别 |
| 乐观并发控制 | 使用版本号或状态条件执行更新，以影响行数判断冲突 | 冲突较少、可重试的更新；属于冲突检测机制，不是先持有互斥锁 |
| 分布式锁 | 利用 Redis、ZooKeeper 等在多个进程间协调 | 跨实例资源协调；必须处理超时、租约、故障和过期持有者 |

读写锁需要实际测试：临界区很短或写入较频繁时，额外协调成本可能抵消读并行的收益。`StampedLock` 的乐观读取不是“不管并发修改直接读”，而是读取临时值后验证 stamp，验证失败就重新读取。[参考：ReadWriteLock](https://docs.oracle.com/en/java/javase/25/docs/api/java.base/java/util/concurrent/locks/ReadWriteLock.html)、[StampedLock](https://docs.oracle.com/en/java/javase/25/docs/api/java.base/java/util/concurrent/locks/StampedLock.html)

### 3. synchronized 锁住的到底是什么？

```java
// 锁当前对象 this；另一个实例不是同一把锁
public synchronized void update() {
    // 修改当前实例的共享状态
}

// 锁指定共享对象；lock 必须由参与协作的线程共同持有
synchronized (lock) {
    // 复合操作
}

// static synchronized 方法锁对应的 Class 对象
public static synchronized void updateGlobal() {
    // 保护与该 Class 锁约定一致的共享状态
}
```

锁有效的前提是所有相关读写都遵守同一保护约定。每次调用都 `new Object()` 作为锁，或者每个请求使用独立服务实例，不能保护所有请求共享的状态。也不要随意使用可能与其他代码共享的字符串常量作为锁对象。

### 4. ReentrantLock 如何正确使用？

```java
public boolean updateWithTimeout() throws InterruptedException {
    if (!lock.tryLock(200, TimeUnit.MILLISECONDS)) {
        return false;
    }
    try {
        // 更新共享状态；lock 是共享的 ReentrantLock 字段
        return true;
    } finally {
        lock.unlock();
    }
}
```

只有成功获取锁后才解锁。超时表示本次没有进入临界区，不代表可以忽略操作结果；业务应明确失败返回或有限重试。公平锁通常需要付出吞吐代价，不能理解为“公平一定更快”。也不能笼统说 `ReentrantLock` 永远比 `synchronized` 快，应按所需能力和竞争负载选型。

### 5. 秒杀扣库存一定要用分布式锁吗？

不一定。单 Redis 实例内的库存检查与预占，可以用 Lua 保证一段执行的原子性；数据库最终扣减可使用 `stock >= quantity` 的条件更新和请求幂等约束。数据库会在执行更新时使用相应的锁，但应用不一定需要再套一层分布式锁。

如果确实使用 Redis 锁，需要唯一持有者标识、原子的比较并删除、合理租约以及对任务超时的处理。租约到期后旧持有者可能仍在执行，新持有者也可能开始工作，续期不能消除所有风险；关键资源可结合版本检查或 fencing token，在资源端拒绝过期执行者。**分布式锁不能替代数据库库存约束，也不能自动覆盖 Redis 与 MySQL 的双写事务。**

`volatile` 也不能代替锁保护复合操作，例如 `stock--`；`Semaphore` 更适合限制同时进入的任务数量，`CountDownLatch` 用于等待完成，不能将所有并发工具都视为同一种互斥锁。

**面试回答：**简单的 JVM 内互斥优先考虑 synchronized，需要超时、中断或多个条件队列时用 ReentrantLock；读多写少可以评估读写锁或 StampedLock；简单状态更新考虑原子类。跨实例的数据约束放在数据库或分布式协调层，秒杀中 Redis Lua、数据库条件更新与幂等常常比全流程套分布式锁更合适。所有方案都要保证锁对象正确、缩小临界区、固定多锁顺序并避免锁内远程调用。

## 三、Redis 宕机后怎么办？以秒杀系统为例，如何恢复数据一致性？

### 1. 先止损，再判断故障类型

| 故障情况 | 处理重点 |
| --- | --- |
| 应用连接失败，但 Redis 服务可能正常 | 检查网络、连接池、超时与故障切换；命令超时可能已执行，不能直接反向补偿 |
| 主节点故障，有可用副本 | 通过 Sentinel 或 Cluster 等机制切换，并检查客户端重连及可能的数据回退 |
| Redis 数据丢失或回到旧版本 | 暂停相关活动放量，根据数据库与持久化任务重建，不能直接继续使用旧库存 |
| 整体服务不可用，暂时无法恢复 | 熔断入口、限制重试、保留已受理任务，向用户展示排队或暂不可用 |

秒杀入口不能在 Redis 不可用时把全部请求直接放到 MySQL，否则可能把库存故障扩大成数据库雪崩。若必须支持降级扣库，需要独立限流、容量验证、数据库条件更新和全局幂等；切换时还要处理此前已受理任务，不能让两条路径重复生效。

### 2. 高可用与持久化能否保证数据完全不丢？

不能直接保证。Redis 主从复制通常是异步的，主节点已返回成功的写入可能尚未到达被提升的副本。Sentinel 或 Cluster 主要改善可用性，不能替代业务对账；`WAIT` 可以提升副本确认程度，但不把 Redis 自动变成强一致系统。[参考：Redis 复制](https://redis.io/docs/latest/manual/replication/)

RDB [+RDB] 是时间点快照，AOF [+AOF] 记录写操作；常见的每秒刷盘策略仍有近期数据丢失窗口。持久化和副本降低风险，却不能单独保证预占、MQ 与数据库结果一致。[参考：Redis 持久化](https://redis.io/docs/latest/management/persistence/)

### 3. 按故障发生的位置恢复

| 故障时点 | 风险 | 恢复方式 |
| --- | --- | --- |
| 请求尚未可靠受理 | 只在应用内或 Redis 内存中的状态可能丢失 | 不承诺已下单成功；依受理协议允许重试或查询 |
| 已受理任务持久化，但尚未执行 | 请求暂时无法处理 | 保留任务，恢复后按相同请求号重试 |
| Redis 已预占，数据库尚未提交 | 缓存恢复后可能缺失或重复预占 | 根据持久化任务重新裁定，数据库条件扣减与幂等兜底 |
| 数据库已提交，Redis 确认失败 | 旧 Redis 库存可能偏大，导致多放入候选请求 | 数据库拒绝超额扣减；根据成功订单修复读模型与预占状态 |
| 数据库确定失败，但回补失败 | Redis 库存偏小，产生少卖 | 根据失败终态和补偿记录幂等回补，不能直接无条件加库存 |

### 4. 一个便于说明的恢复流程

对于某个活动或 SKU，可以采用“冻结、收敛、重建、校验、恢复”的方式，优先保证安全：

1. **冻结写入入口：**暂停新预占，并控制相关消费者、取消和补货流程。单纯停 HTTP 接口不足以停止 MQ 中的在途任务。
2. **隔离旧执行者：**使用活动代次或版本校验等机制，在关键写入处拒绝旧任务、旧消费者和旧回补继续修改新库存。新建一个 Redis key 本身不能阻止旧任务更新数据库。
3. **收敛已受理请求：**根据持久化任务、订单和库存流水，将存量任务处理为成功或确定失败。必要时在限流下通过数据库完成处理；正在提交的请求应先等待、查询并确定结果，不能直接判失败。
4. **重建库存状态：**在确认该范围内没有未计入的有效预占、且采用一致业务截止点后，以数据库剩余库存初始化新版本 Redis，并恢复仍需要保留的限购与请求幂等信息。
5. **校验并逐步恢复：**核对库存和订单数量，验证旧任务隔离、重投幂等和结果查询，再灰度放量，持续观察预占、落单、失败与补偿指标。

如果为缩短恢复时间而保留待处理预占，则应在同一截止点从数据库剩余库存中扣除尚未生效的有效预占数量，且不能将已提交但未确认的请求再次扣除。与“先收敛全部任务再重建”相比，这种恢复方式需要更严格的状态与位点控制。

不能直接执行“读 MySQL 库存 → SET Redis 库存”后立即开流量：读与写之间可能还有扣减，旧回补可能晚到，限购信息也可能丢失。恢复库存数值只是其中一步，恢复任务处理状态和约束同样重要。

### 5. 最终一致性依赖哪些长期机制？

- **可恢复的数据源：**订单、扣减流水、受理任务及结果不能只存于可能丢失的缓存。
- **幂等与唯一约束：**同一请求、同一补偿重复执行不产生额外库存变化；业务限购有独立约束。
- **结果可判定：**订单成功、失败与取消有明确互斥状态，不用超时猜测结果。
- **重试与对账：**失败任务可重投、异常可告警、长期不收敛任务可人工处理。
- **恢复时的隔离：**阻止旧活动、旧消费者或迟到消息污染新版本状态。

**面试回答：**Redis 宕机先限制秒杀入口并确认故障，不把所有流量直接打到数据库。主从切换和持久化改善可用性，但仍可能丢预占数据，因此我会依靠数据库订单、库存流水和持久化受理任务裁定结果。恢复时控制在途写入、隔离旧执行者，收敛任务后重建库存与限购状态，再逐步放量。数据库条件更新防超卖，幂等和补偿处理重复或遗漏，对账保证长期收敛。

[+Outbox]:
  Outbox（事务发件箱、本地消息表）将业务记录与待发送事件放在同一本地数据库事务中提交，再由独立程序或变更订阅可靠投递。它解决业务落库与事件记录的原子性，不自动保证消息只发送一次，也不能将已经完成的 Redis 操作纳入同一数据库事务。

[+CAS]:
  CAS（Compare-And-Swap，比较并交换）在预期值仍匹配时原子更新共享值，否则失败或重试。常用于原子类；多字段整体一致性、ABA 问题和高竞争下的重试成本仍需额外考虑。

[+RDB]:
  RDB（Redis Database）持久化将某个时点的数据保存为快照，便于恢复。快照之后且尚未进入后续持久化结果的变化，可能在故障后丢失。

[+AOF]:
  AOF（Append Only File，追加日志文件）通过记录写操作支持恢复，数据安全边界受刷盘策略及故障情况影响。每秒刷盘通常存在约一秒量级的近期数据丢失窗口，不能等同于零丢失。

*[CAS]: Compare-And-Swap，比较并交换；基于预期值匹配执行原子更新。
*[RDB]: Redis Database，Redis 的时间点快照持久化方式。
*[AOF]: Append Only File，追加日志文件；Redis 的写操作日志持久化方式。
